# t3-fleet-gateway design

Status: accepted for v0.1. This document is the build specification and stays as the architecture reference. Update it when behavior changes.

## Outcome

Cloud agents, starting with Grok Bot, can hand coding work to T3 Code servers on your machines and follow it to completion. The agent names the task and project, or a machine when no project is named. The gateway routes the task, starts its workspace and T3 thread, and watches it. Named projects use a fresh git worktree per job by default; unnamed work can use the machine's T3 scratch workspace. Every job is an ordinary T3 thread you can open, read and interrupt.

### In scope for v0.1

- One gateway process on an always-on machine, reachable over public HTTPS through a tunnel the operator provides.
- Agent-facing MCP server (Streamable HTTP) with the gateway's own OAuth 2.1 authorization server, including refresh tokens, so agents stay signed in.
- Downstream MCP client to one or more T3 Code servers, with credentials the gateway obtains and renews itself through T3's pairing-code approval.
- A durable job ledger in SQLite, the tools below, a background watcher, and an operator CLI.
- Multi-host configuration and routing by project. The first deployment enrolls one host; adding a second host is configuration plus enrollment, not new code.

### Out of scope for v0.1

- Patching T3 Code. Gaps are worked around in the gateway.
- Managing hosted agent routines. Agents configure their own polling schedules or opt-in outbound webhook triggers (see "Outbound job webhooks").
- Multi-user tenancy. One operator; agents are that operator's clients.
- Queues across hosts, automatic host failover, PR management, model selection heuristics.
- A general administration UI. The opt-in operator dashboard has monitoring and, since v0.1.9, webhook connection management on a listener of its own; see "Operator dashboard". It also supports confirmed job settlement; it has no host or client controls.

## Architecture

```
Agent (Grok Bot, any MCP client)
   │  HTTPS, OAuth 2.1 (gateway-issued tokens; audience = this gateway)
   ▼
t3-fleet-gateway  ── SQLite (clients, tokens, hosts, jobs, events)
   │  MCP client per host, bearer token issued by that host's T3 (audience = that T3)
   ▼
T3 Code server(s)  ──► T3 threads in per-job git worktrees (or a machine's scratch workspace)
```

Two credential audiences never mix. Agent tokens are only valid at the gateway. T3 tokens never leave the gateway.

### Runtime

- Node.js 24.22.1+ on 24.x or 26.12.1+ (Node itself blocks the compromised eMudhra intermediates; `src/nodeVersion.ts`, enforced by the launcher) running TypeScript directly (type stripping, no build step). ES modules, `.ts` import specifiers, erasable syntax only.
- SQLite through `node:sqlite`, WAL mode, `busy_timeout` set, migrations versioned in code (append-only; a migration that must rebuild a table runs with foreign keys off and checks them before committing).
- The official MCP TypeScript SDK for both the server and the client: the v2 split packages `@modelcontextprotocol/server` and `@modelcontextprotocol/client` (2.3.x). v2 is the SDK's stable, documented line (the v1 `@modelcontextprotocol/sdk` package is the previous generation, and its docs point new work at v2). The split packages are also far lighter: the server needs only `zod` and the shared core, while 1.x pulls in Express, Hono, CORS and rate-limit middleware we would not use. v2 serves 2025-era clients (Grok Bot today) and 2026-07-28 clients from one endpoint. v2 no longer ships authorization-server helpers (they are frozen in a legacy package), so the gateway implements its small OAuth server directly on `node:http`.
- Runtime dependencies: the two SDK packages and `zod` (the SDK's schema library, also used for config and tool input validation). Nothing else.
- Tests with `node:test`. Typecheck with `tsc --noEmit`.

### Process layout

One process, `t3-fleet-gateway serve`, runs the HTTP server, the watcher loop, the dispatcher, and credential renewal. A CLI with the same entrypoint manages it. The CLI and the server share the SQLite database, so CLI actions (minting an approval code, revoking a client) take effect without a restart.

## Configuration and data

Nothing machine-specific lives in the repository.

- Config file, JSON: `$T3FG_CONFIG` or `~/.config/t3-fleet-gateway/config.json`.
- Data directory: `$T3FG_DATA_DIR` or `~/.local/share/t3-fleet-gateway/`. Created with mode `0700`; the database and key files with `0600`. Startup refuses to run if they are group- or world-readable.
- A committed `config.example.json` uses only placeholder values (`example.ts.net`, `/path/to/repo`).

Config fields (validate on load with clear errors):

```jsonc
{
  "publicUrl": "https://gateway.example.ts.net:8443",   // origin agents use; OAuth metadata derives from it
  "listen": { "host": "127.0.0.1", "port": 3790 },
  "hosts": [
    {
      "id": "main",                                      // stable short id used in project config and output
      "label": "Always-on workstation",
      "t3Url": "http://127.0.0.1:3773",                  // loopback http, or https for a remote host
      "mintPairingCode": ["t3", "auth", "pairing", "create", "--ttl", "5m", "--json"],
      "access": "auto",                                  // T3 approval level the gateway requests; a ceiling for runtimeMode
      "maxConcurrentJobs": 2,
      "defaultModelSelection": null,                     // modelSelection for projects on this host that set none
      "discovery": {                                     // opt-in; all off by default (see "Discovery" under Jobs)
        "enabled": false,                                // agents may list this host's T3 projects and model catalog
        "allowWorkStart": false,                         // work_start may target an unconfigured T3 project here by id
        "runtimeMode": "approval-required",              // policy for such launches
        "baseRef": "main",
        "branchPrefix": "fleet/"
      }
    }
  ],
  "projects": [
    {
      "alias": "pilot",                                  // what agents use
      "description": "Scratch repo for gateway tests",   // shown to agents
      "host": "main",
      "t3ProjectId": "…",                                // or "t3ProjectTitle" resolved at startup
      "baseRef": "main",
      "branchPrefix": "fleet/",
      "runtimeMode": "approval-required",                // T3 runtime mode for job threads
      "modelSelection": null,                            // optional T3 modelSelection object; else the host's, else T3's project default
      "allowWorkStart": true                             // false: agents drive the project's standing jobs only (work_start refused)
    }
  ],
  "tokens": { "accessTtlSeconds": 43200, "refreshIdleTtlDays": 90 },
  "renewal": { "renewWhenDaysLeft": 5, "checkEveryMinutes": 60 },
  "watcher": { "pollSeconds": 10, "reconcileWindowMinutes": 10 }
}
```

`runtimeMode` defaults to `approval-required` when omitted. Operators choose looser modes per project deliberately. As built: the gateway cannot answer permission approvals, so `approval-required` jobs wait for the operator in T3, and unattended projects need `auto` or `full-access`. T3 refuses a launch without `modelSelection` when the T3 project has no default model (`invalid_request`), so `doctor` checks that every project has a model from its own `modelSelection`, its host's `defaultModelSelection` or the T3 project's `defaultModelSelection`, and `serve` logs `project.model_missing` at startup otherwise.

Validation rules beyond types (see `docs/configuration.md` for every field):

- `publicUrl`, `t3Url` and `allowedOrigins` entries are origins only; `http` is accepted only for loopback hosts.
- `listen.host` must be a loopback address.
- T3 `access` is one of `read-only`, `approval-required`, `auto-accept-edits`, `auto`, `full-access`. T3 treats it as the ceiling for thread runtime modes, so a project's `runtimeMode` may not exceed its host's `access`, and a `read-only` host carries no projects.
- Optional `allowedOrigins` (default empty) lists extra `Origin` values `/mcp` accepts besides `publicUrl`.
- `hosts[].discovery.allowWorkStart` requires `discovery.enabled`, and then `discovery.runtimeMode` may not exceed the host's `access`. A `read-only` host may enable discovery for browsing only.

## Agent-facing authorization (gateway as OAuth server)

Follow the MCP authorization spec (2025-06-18) and OAuth 2.1:

- `GET /.well-known/oauth-protected-resource` and `/.well-known/oauth-protected-resource/mcp`: resource = `${publicUrl}/mcp`, authorization server = `publicUrl`.
- `GET /.well-known/oauth-authorization-server`: issuer, endpoints, `code_challenge_methods_supported: ["S256"]`, `grant_types_supported: ["authorization_code", "refresh_token"]`, `token_endpoint_auth_methods_supported: ["none"]`, scopes.
- `POST /oauth/register`: dynamic client registration (RFC 7591), public clients only. Accept loopback `http` and any `https` redirect URIs (hosted agents such as Grok Bot use an `https` callback on their provider's own domain). Reject fragments, credentials in URLs, non-http(s) schemes. Store the client; cap name and redirect counts and lengths.
- `GET /oauth/authorize`: validate client, redirect URI exact match (as built: `http` loopback URIs match with any port, per RFC 8252 section 7.3), PKCE S256, `resource` (if present) equals ours, scopes. Render the approval page. Never redirect for an invalid client or redirect URI.
- Approval page: server-rendered HTML, no external assets, strict CSP, `X-Frame-Options: DENY`. Shows the client name, the redirect origin in full, and requested access. The operator enters a one-time approval code and chooses **Read** (`fleet:read`) or **Operate** (`fleet:read fleet:operate`). The form carries an HMAC of the authorization request to prevent tampering. As built since v0.1.5, the operator also chooses **All machines** (those fleet scopes) or **Selected machines** (host scopes for the ticked hosts; see "Per-host grants" below).
  - As built: the form never answers with a redirect to the client. Approval, denial and request errors answer `200` with a return page that navigates to the redirect URI by `<meta http-equiv="refresh">` and shows a Continue link (`renderReturnPage`), and the CSP's `form-action` is `'self'` only. An approved form submitted again (same signature) shows the same authorization response as a link while its code is pending, then "already approved" until the form would have expired; it never issues a code or records a failure (`src/oauth/approvedRequests.ts`, in memory).
- Approval codes: minted by the CLI (`t3-fleet-gateway pair --ttl 15m`), stored hashed, single use, expire. Throttle failures: per authorization request and globally (for example 5 per request, 20 per hour), then refuse new attempts for a cool-down and log it.
  - As built: codes are 10 Crockford base32 characters (50 bits), shown as `XXXXX-XXXXX`, accepted in any case and spacing, stored as HMAC-SHA256 under the server key, TTL 15 minutes by default (1 minute to 24 hours). After 5 failures an authorization request is locked; after 20 failures in a rolling hour all approvals are refused until the hour clears (that window is the cool-down) or the operator mints a new code: minting marks earlier failures as no longer counting globally (`approval_failures.counts_globally`), since anyone who can reach the page could otherwise keep the operator locked out. Per-request locks stay. The approval form expires 10 minutes after it is rendered.
  - Registration is limited to 30 new clients per hour. A client without a completed authorization stops counting after 10 minutes, and clients that never complete an approval are deleted after a day.
  - `t3-fleet-gateway throttle status` shows both global limits; `throttle reset` deletes recorded approval failures (lifting per-request locks too) and stops existing registrations from counting (`oauth_clients.counts_toward_limit`).
- `POST /oauth/token`:
  - `authorization_code`: single-use codes (60 s), PKCE verification, redirect URI and client match, `resource` match. Issue an access token and a refresh token.
  - `refresh_token`: rotation. The new pair replaces the old. Reuse of a rotated refresh token after a short grace window (about 2 minutes, to absorb client retries) revokes the whole token family. Refresh tokens expire after `refreshIdleTtlDays` without use.
    - As built: a rotated token presented again within 2 minutes (a lost response, or concurrent requests refreshing with the same token) gets another pair, a sibling of the first; siblings coexist, so whichever pair the client saved works. When any sibling is first rotated, the other siblings are superseded and the parent can no longer be retried. Presenting a superseded token, or a rotated one after the grace window or after one of its children was rotated, revokes the family. Each refresh token records the token it was issued from (`refresh_tokens.parent_hash`).
- Tokens are random 256-bit values, stored only as SHA-256 hashes. Access tokens are bound to the resource and scopes.
- `/mcp` requires `Authorization: Bearer`; failures return 401 with `WWW-Authenticate: Bearer resource_metadata="…"`. Insufficient scope returns a clear tool error naming the missing scope.
- CLI: `clients list`, offline `clients diagnose <id>`, `clients revoke <id>` (revokes all tokens for the client). List uses total and unrevoked family counts: `pending` only for no family, `grants revoked` for all families revoked, and `unrevoked` for at least one unrevoked OAuth family, not proof of usability. Client revocation takes precedence. Diagnosis checks actual grant state for the configured resource, including precise expiry, rotation/grace, child rotation, supersession, replay and revocation. Counts and expiry ranges are per state and per family, aggregated across all families; no token/hash leaves the diagnostic function (`src/oauth/diagnostics.ts`). Usable server grants do not identify which sibling the connector saved. Offline reachability remains unknown; `doctor` tests the operator route and downstream credentials separately, never the cloud connector route.
- Migration 7 adds nullable `oauth_clients.last_mcp_success_at` and `last_refresh_success_at`, with no backfill from the mixed `last_used_at`. Completed authorized MCP HTTP 2xx/202 exchanges (including valid tool errors) update the former at most once per minute, only on response `finish`; rejected auth/Origin and malformed/failed HTTP do not count. Bookkeeping failure logs a fixed event and cannot change the response. Successful refresh pair issuance, including a grace retry, updates the latter transactionally on every success; no attempted/rejected refresh counts. Null means unknown: old history or never observed. Legacy `last_used_at` behavior is retained.
- As built, for agents that cannot sign in with OAuth (Notion's custom MCP connections offer only header authentication): `clients token --name <name> [--access operate|read] [--hosts all|<id>,<id>] [--ttl <duration>|never]` mints a bearer token, printed once. It is a client of its own (no redirect URIs, so it can never complete an authorization; `counts_toward_limit` 0) with one token family and one access token (default 1 year, from 1 hour to 100 years; `never` stores `NEVER_EXPIRES`, `Number.MAX_SAFE_INTEGER`) and no refresh token (`refresh_token_hash` is empty, which matches no refresh token). It is verified, scoped and revoked exactly like an OAuth access token, using the same authorization checks as OAuth. `clients list` shows it as `bearer token` with its expiry, and its status as `expired` once past it.

- Bearer rotation: migration 20 adds `operator_tokens` (random public ID, access-token hash reference, nullable last tool use) and `operator_token_calls` (per-token UTC-hour counts). Existing bearer tokens receive IDs with unknown usage history. `clients tokens <clientId>` reports only IDs and safe metadata. `clients rotate <clientId> --token-id <id> --overlap <duration> [--ttl <duration>|never]` atomically creates a replacement in the same family with identical scopes and shortens only the selected old token's expiry to the earlier of its original expiry and the overlap deadline. Overlap is mandatory, 0 to 30 days; replacement TTL follows issuance defaults. Repeated rotations never extend prior deadlines. `clients revoke-token` sets the selected access token's revocation immediately; whole-client revocation still invalidates all siblings. Only hashes of secrets are persisted. Schema-valid authenticated tool invocations (including refused/failed tools, excluding handshakes and authentication failures) update last use and counts; current-hour and 24-hour counts mean this UTC hour and the previous 23 buckets. Older buckets are pruned on a call and excluded from reads. Observability failure cannot change a tool response.

### Per-host grants

As built in v0.1.5. A grant covers either every host or selected hosts, encoded in its scope string, so no schema change was needed:

- **Fleet scopes** `fleet:read` and `fleet:operate` cover every configured host, including hosts added later. Every grant and bearer token from before v0.1.5 holds only these, and keeps exactly that meaning: no reauthorization, revocation or URL change. *All machines* on the approval page and `clients token` without `--hosts` (or with `--hosts all`) issue them. They stay the only scopes in the authorization server and protected-resource metadata (`scopes_supported`), so SDK clients, which request the advertised scopes, ask for what they always did and the operator picks the machines on the page.
- **Host scopes** `host:<id>:read` and `host:<id>:operate` (`<id>` a host id: lowercase letters, digits and hyphens, up to 32) cover one host. *Selected machines* and `clients token --hosts <id>,<id>` issue them for each selected host (Operate: both, Read: read only), and no fleet scope.
- Permissions are the union of what each scope allows: read on host *h* needs `fleet:read` or `host:h:read`, operate needs `fleet:operate` or `host:h:operate` (`src/oauth/scopes.ts`, `permits`). Grants are positive only, so dropping a scope string can only remove access; a restricted grant that loses its host scopes is empty, never fleet-wide. A stored scope string with any unrecognized or malformed part grants nothing (`parseScope` fails, as before for unknown scopes). A host scope naming a host no longer configured grants nothing live, though it still matches ledger rows recorded with that host id, and applies again if a host with that id is configured.
- Selection on the approval page (`hosts_mode` `all` or `selected`, repeated `host` fields) is validated before the approval code is redeemed or a failure recorded: selected with nothing ticked, an unconfigured id, ticked hosts with `all`, a repeated or unknown mode are refused and the page is shown again. Every refused form (a wrong approval code too) is shown again with the operator's choice, not the request's defaults, so a retry that corrects only the code grants what was chosen (`submittedChoice`): the access level if valid, otherwise neither; ticked hosts that are configured, never other submitted values; *All machines* only for exactly `hosts_mode=all`, otherwise *Selected machines*; and no checked choice the request's ceiling disables. A retry of an empty, unknown or malformed choice is therefore refused again, never taken for all. A form from before v0.1.5 sends neither field and means all, as it did then; it is shown again with the page defaults. The authorization request's own scope is still part of the signed form; the machine choice, like Read/Operate, is the operator's. An authorization request naming host scopes must name configured hosts (`invalid_scope` otherwise) and sets a ceiling: the grant must be covered by the request (`withinRequest`), and choices beyond it are shown disabled. Requests with fleet scopes or none leave the choice to the operator, as before. The page lists every configured host's label and id.
- Refresh (`narrowScopes`): without `scope` the grant is kept. With `scope`, each requested scope must be one the grant holds, except that a fleet scope requested of a grant restricted to selected hosts stands for that grant's host scopes at the same level, so a client that knows only the advertised scopes keeps exactly its hosts and never gains others; anything else is `invalid_scope` and leaves the grant untouched. The installed MCP client SDK sends no `scope` on refresh. Rotation, the grace window, replay detection and resource binding are unchanged; a narrowed refresh token is the ceiling for its own later refreshes.
- Enforcement is in the job layer, from the job's stored `host_id`, before any T3 call or ledger data is returned (`JobService`): the tool registry requires the tool's level on at least one host; `work_status`, `work_messages`, `work_continue`, `work_respond`, `work_cancel` and `work_settle` treat a job on a host where the caller has neither the requested permission nor Read as an unknown job id (`not_found`, the same text), and one it can read but not operate as `insufficient_scope`. Host filtering happens in SQL, so a job the caller may not see is never read for it, whatever its stored launch spec holds. An Operate-only scope retained by refresh can still perform a mutating operation on its host. A repeated `work_continue` request id is checked only after authorization. `work_start` checks a repeated request id against the host of the job it already started before resolving the current alias, and checks the current project host for new work (a project alias moved to another host in the config cannot return a job elsewhere; `insufficient_scope`, naming neither job nor host), and `start_disabled` names only standing jobs the caller can see. `work_list`, `work_feed` events and attention filter by host in SQL (`JobStore` `JobScope`) together with `mine`, before their limits, so hidden jobs never take a place on a page; cursors stay global event ids, exclusive. `fleet_status` lists, counts and health-checks only readable hosts, with their projects and standing jobs. Unknown projects are reported with a list of visible ones only. The engine, the operator CLI and stored data are unaffected.
- CLI: `clients list` shows granted access per client (`operate (all hosts)`, `operate: main, studio`, `read: main`), `clients diagnose` each grant's access and any of its hosts that are no longer configured; no token or hash is printed. `--hosts` accepts `all` or a non-empty comma-separated list of configured host ids; anything else is refused before a client or token is stored.

### Per-client project access

Migration 21 adds `client_project_access`, an optional client row containing up to 100 host-bound project grants. No row means unrestricted; an empty array denies every project; malformed policy fails closed. The operator replaces a list with `clients projects <id> --project <alias> [--project @host/projectId ...]`, inspects it without flags, denies all with `--no-projects`, or removes the restriction with `--all-projects`. It is a client ceiling shared by all OAuth grants and bearer tokens, retained during rotation. It never confers a host, Read/Operate level or external-thread scope.

A configured alias grant covers that alias on its host, and records its explicit T3 id when pinned, so jobs retain access to that project by id too. An explicit id grant covers the exact host/id and its configured pinned aliases, including queued alias jobs. A title-only alias is usable by alias without discovery at acceptance; discovery maps it to an id only when the title resolves uniquely. Grant a title-only alias itself to accept work by that alias before dispatch. Alias grants follow operator configuration for that alias; use explicit ids for stable identity across alias changes.

Job queries intersect project and host predicates in SQL before parsing, limits, feed pagination and attention. Point access outside a restricted client's list returns the fixed `insufficient_scope` project permission message; an unknown id may return the same message, so it cannot reveal whether an excluded job exists. Host authorization still comes first. `work_start` replays are reauthorized against their recorded job, not the current alias; queued dispatch checks the current project policy again before launch. Unrestricted alias-only starts retain their no-discovery behavior and request-id hashes.

`fleet_projects` filters the shared catalog before totals and pagination. `fleet_status` filters aliases, standing jobs, scratch defaults and host job counts. `fleet_threads` and adoption authorize the project before touching thread caches or thread reads; all job actions use the same project guard, including messages, continue, respond, cancel and settle. The private operator dashboard and local operator commands remain fleet-wide.

Bot-owned notification connections, and client-filtered routes for that bot, intersect their existing filters with current project access at capture, replay, claim and immediately before sending. Tightening access prevents later sends of already captured denied payloads; a POST already handed to the network cannot be recalled. Archives retain immutable original payloads, but replay selects authorized jobs before its page limit. Notification connection metadata and bindings are filtered; `healthAvailable: false` marks withheld aggregate history (health counters are placeholders), since connection-wide counts could reveal excluded projects. Credential alerts for a restricted bot require an affected allowed job bound to that same connection. Generic operator destinations without a bot association retain their existing fleet-wide role. No budget, cap or model allowlist is introduced.

## Agent-facing MCP server

- Streamable HTTP on `POST /mcp`. Stateless mode with JSON responses (survives restarts, no session affinity). 2026-07-28 requests go to the SDK's `createMcpHandler`; 2025-era requests (classified with the SDK's `isLegacyRequest`) are served by a fresh stateless `WebStandardStreamableHTTPServerTransport` per request with `enableJsonResponse`, because the handler's built-in legacy fallback always answers with an SSE stream. `GET` and `DELETE` on `/mcp` answer `405`: there are no sessions to stream or end.
- Must accept in-session requests that omit `MCP-Protocol-Version` (observed from Grok Bot's client). Add a regression test.
- Origin header validation per the spec's DNS-rebinding guidance, without breaking server-to-server clients that send no Origin. As built: a request with an `Origin` other than `publicUrl` or an `allowedOrigins` entry gets `403`; no `Origin` is accepted. The `Host` header is not validated, because tunnels differ in what they forward and every `/mcp` request needs a bearer token anyway.
- Tool results: `structuredContent` plus a human-readable `text` summary. Actionable question data is included in text too, for clients that ignore structured content. Errors as tool errors (`isError: true`) with a stable `code` and actionable message.

### Tools

Scopes: **read** = `fleet:read`, **operate** = `fleet:operate`, or the same level on the job's or project's host for a grant restricted to selected hosts (see "Per-host grants").

| Tool | Scope | Purpose |
| --- | --- | --- |
| `fleet_status` | read | Hosts (reachable, T3 version, credential expiry or `rejected` when T3 answers 401/403, running and queued job counts, `discovery` flags, `defaultProject`: the machine's scratch alias for work with no named project, or null), configured projects (alias, description, host, `workspaceMode`, `runtimeMode`, `modelConfigured`: whether the gateway config sets the model, `allowWorkStart`, and `standingJobs`: the project's open standing jobs with job id, title, state and link), gateway version. "Running" counts the launched jobs in states that hold a concurrency slot: `dispatching`, `running`, `needs_input`, `cancel_requested` and `unknown`. |
| `fleet_projects` | read | On hosts with `discovery.enabled`: the T3 projects (id, name, whether T3 has a default model) with the launch policy that applies to each (`launch.alias` to pass as `project`, or `target` by id when allowed) and a guidance line. Hosts without discovery or that cannot be read are listed as unavailable with an error code. Paged per host. See "Discovery" under Jobs. |
| `fleet_threads` | read + threads:read | Threads in one host/project, including those opened in T3; bounded snapshot pagination with ownership metadata. |
| `work_adopt` | operate + both thread scopes | Read-only import of an external thread into the job ledger. |
| `fleet_models` | read | On hosts with `discovery.enabled`: provider instances, models and their advertised options (`select` with choices, `boolean`), flat and paged per host, plus every provider (including those with no models) with T3's `canRunChildTask`, `canRunCrossProviderChildTask`, `runtimeModes` and `constraints` as metadata. Text output includes every id and choice. |
| `work_list` | read | Jobs filtered by project alias (or internal `@<host>/<projectId>` ref), by `target` (host and T3 project id) and state, newest first, bounded. |
| `work_status` | read | One job: state, project, host, `workspaceMode`, T3 thread id, title and app link, branch (empty for a scratch job), timestamps, pending requests, latest worker message excerpt (bounded, with `excerptTruncated`), whether it waits on work it delegated, live `settled` / `settledAt` (null when unknown), last error. |
| `work_messages` | read | A job's worker messages in full (up to 50,000 characters each), read live from T3: the latest by default, paged back with `before` and forward with `after`. |
| `work_feed` | read | Events since a cursor (state changes, needs input, finished turns, failures) plus the list of jobs currently needing attention. Returns the next cursor. Designed for an agent's scheduled routine. |
| `work_start` | operate | Start a job from a task description and optional base64 attachments, with no named project on a chosen machine (`target: { host }`), in a configured project (`project`) or, on a host with discovery, a T3 project by id (`target: { host, projectId }`), optionally with an explicit `modelSelection` from `fleet_models`. Idempotent on `requestId`. |
| `work_continue` | operate | Send a follow-up instruction and optional base64 attachments to a job's thread. Idempotent on `requestId`; uncertain attachment sends stay blocked without resending. |
| `work_respond` | operate | Answer a pending T3 question on a job. (Permission approvals cannot be answered through T3's tools; see "As built" under Jobs.) |
| `work_settle` | operate | Settle a quiet finished job's T3 thread; fresh status and delegated-work check, confirmed by a read back. Idempotent on `requestId`. |
| `work_cancel` | operate | Interrupt a job's thread. Reports requested versus confirmed. On a standing job, interrupts the current turn only. |

Tool descriptions are written for an LLM: what the tool does, when to use it, idempotency rules, and the state meanings.

`work_start` and `work_continue` accept `attachments: [{ name?, mimeType, data }]`: base64 bytes, at most 8 files, 5 MiB each and 10 MiB total. They upload to the destination T3 host and use native image/file metadata. URLs are unsupported. Request hashes include metadata and content hashes; text-only hashes remain unchanged. Migration 17 adds the private `job_launch_attachments` table for queued starts; ordinary job reads never load these payloads. Attachment follow-ups use T3's API without a retry key: a durable attempt marker prevents duplicates after uncertainty, and success reports `delivery: accepted` without guessing new-turn attribution. [Exact schema, storage, retry semantics and T3 source evidence](attachments.md).

As built, tools are registered in this order: `fleet_status`, `fleet_projects`, `fleet_models`, `fleet_threads`, `work_start`, `work_adopt`, `work_continue`, `work_respond`, `work_cancel`, `work_settle`, `work_status`, `work_messages`, `work_list`, `work_feed` (`src/mcp/fleetStatus.ts`, `src/mcp/catalogTools.ts`, `src/mcp/workTools.ts`). Job errors use these stable codes besides the shared ones: `not_found` (job, project, host or pending request), `job_state_conflict` (the job's state does not allow the operation), `request_id_conflict` (a requestId reused with different input for the same tool), `start_disabled` (`work_start` in a project with `allowWorkStart: false`, or into an unconfigured T3 project on a host whose `discovery.allowWorkStart` is false; the message names the project's standing jobs or the aliases that accept work; a retry of a request id the agent used before the setting changed still returns its job), `discovery_disabled` (a `target` or `modelSelection` for a host without `discovery.enabled`; also the per-host error in `fleet_projects` and `fleet_models`), `catalog_limit` (a host's catalog exceeds the gateway's bounds and is reported unavailable rather than cut), and T3 transport codes `host_unreachable`, `t3_timeout`, `t3_response_lost`.

## Jobs

### States

`queued → dispatching → running ⇄ needs_input → idle`, plus `cancel_requested → cancelled`, `failed`, and `unknown`. Standing jobs (below) start in `running`, `needs_input` or `idle` and end in `released`.

- `idle`: nothing runs on the thread; the worker's turn is over. This is "read the reply, then review or instruct", not proof the task met its goal. `work_continue` moves it back to `running`. A worker that delegated work to other threads (a coordinator) is idle while that work runs and starts its next turn by itself when it is done (`waitingOnDelegatedWork`, below).
- `needs_input`: T3 reports pending approvals or questions for the thread.
- `unknown`: the gateway cannot tell whether a launch happened (for example the response was lost). Never auto-retried. Reconciliation resolves it.
- `released`: the operator stopped following a standing job. The T3 thread is untouched.
- A worker turn failure is `idle` with `lastError.code: t3_run_failed`, for launched and standing jobs alike.
  The thread is still followed at the existing one-minute idle polling cadence; `work_continue` resumes it with the usual
  idempotency and root-reservation rules. A new active/blocked turn or a later finished turn clears the error and atomically
  appends `job_recovered` (reason `worker_resumed`) alongside the normal state/turn event. Repeated snapshots do not emit recovery.
  A failed later turn retains the error. Settlement acknowledges attention until subsequent turn activity; it never ends tracking.
  Failure webhooks retain type `failed` with job state `idle`; recovery uses the normal opt-in `running` or default `idle`
  notification, with `job_recovered` available in the feed. Default subscription events and identities are unchanged.
- Terminal: `cancelled`, `failed` (launch failure or missing thread), `released`. Host unreachability is an observation recorded on the job, not a failure.

Migration 16 reclassifies existing `failed` jobs with `t3_run_failed` and a thread id as `idle`, clearing only `finished_at`.
It preserves failure diagnostics, activity timestamps, settlement acknowledgments and immutable queued webhook payloads;
reclassification itself sends no notifications. Older gateway builds refuse the newer ledger. A resumed old job is discovered
on the next idle poll without relaunching or resending anything. All other failed and cancelled jobs stay terminal.


Every transition appends to `job_events` (append-only) with a monotonically increasing id that serves as the feed cursor.

### Starting a job

1. Validate scope, project alias, task size. Look up `(clientId, requestId)`: same request and same input hash returns the existing job; same request with different input is rejected.
2. Insert the job as `queued` with a short job id, in one transaction with its first event. Worktree jobs have branch `${branchPrefix}${jobId}`; scratch jobs store an empty branch.
3. The dispatcher takes queued jobs while the host is below `maxConcurrentJobs`, marks `dispatching`, then calls `t3_thread_launch` with `title` containing the marker `[job:<jobId>]`, `projectId` and `workspaceStrategy: { type: "worktree", baseRef, branch, startFromOrigin: false }` for worktree jobs or, for a scratch alias, `scratch: true` and neither of those (T3 refuses `scratch` together with either, files the thread under its own scratch project and gives it a folder of its own), `runtimeMode`, optional `modelSelection`, and `message` = task plus a short footer naming the job id.
4. Success records the thread id and moves to `running`. A definite rejection (validation error) moves to `failed` with the reason. Anything ambiguous (timeout, connection reset after sending) moves to `unknown`.

### No named project

When the user names a machine but no project, use `work_start { target: { host: "machine-a" }, task, requestId, title? }`. `defaultProject` must name a configured scratch alias on that same host; discovery is not needed. A missing default is `not_found`. Existing host grants, `allowWorkStart`, runtime access ceilings and model defaults apply. A host-only start is an alias-policy launch, so its metadata source stays `alias`; `discovery.allowWorkStart` controls unconfigured named projects only.

The operator configures one identity for scratch. For example, the host has `"defaultProject": "machine-a-scratch"`, and that alias has `"host": "machine-a", "workspaceMode": "scratch", "t3ProjectId": "<T3_SCRATCH_PROJECT_ID>"`. `workspaceMode` defaults to `worktree` on existing aliases. A scratch alias requires an explicit id; title-only lookup such as `"No project"` is refused. The pin must be the id of T3's internal scratch project (shown as "No project" in T3), because it is how the gateway checks, right before a launch, that the project still exists on the host, and where it looks for a thread whose launch response was lost. It is attested by the operator: the gateway cannot read a project's root from its sanitized catalog. A scratch launch sends no project id: T3 chooses the scratch project and a folder for the thread. If T3 answers with another project id than the pin, the job follows the thread anyway and the gateway logs the fixed warning `job.scratch_project_mismatch` (job and host ids only); a lost launch response is then not found by the project-scoped lookup and ends as `launch_not_confirmed`. A scratch pin may not be shared with a non-scratch alias on the same host (`config_invalid`). The gateway's sanitized project catalog does not expose the project root and cannot independently attest that classification. Verify the id in T3 before configuring it. No caller may supply a root path, worktree path, branch or root execution strategy.

An explicit scratch alias (`project: "machine-a-scratch"`) and the host-only start are recorded from the configuration alone, with no read of T3: they work with the host down (the job is `queued`), and no T3 project name is recorded (`projectName` is null). An explicit model selection needs discovery and is validated against the host's fresh capabilities. A direct `target: { host, projectId }` still resolves to every configured alias policy, including a pinned scratch alias's workspace mode and restrictions. Named ordinary projects keep fresh worktrees. Resolve an unknown named project or report it; never fall back to scratch.

Scratch launches always record a v2 `launch_spec` before queueing, including host id, the configured pin, alias, runtime, model (the exact selection, or the configured or T3 default) and the workspace (`scratch`, with no branch or base ref; worktree launches stay version 1). Host-only requests also record the default alias binding. Their request-id hash covers the original host-only intention before resolution, so changing a default does not change a replay or move its existing job. Dispatch reads the host's project list and rechecks that the pin still exists and maps to the alias, and that the recorded host, workspace mode, default binding and runtime policy still apply and the alias still accepts work. A changed binding fails with `launch_policy_changed` before a launch. Model defaults are frozen; explicit model selections are validated again. Lost responses remain `unknown` and reconcile only on the recorded host/project, even after configuration changes or a restart; they are never relaunched.

Version 1 specs retain their worktree meaning. Legacy alias-only worktree starts retain their exact request-id hashes and make no downstream calls until dispatch. A stored spec this build cannot read (malformed, or a version it does not know) is never treated as a legacy job and never fails a read: the job carries `launchSpecUnreadable`, a queued one fails at dispatch with `database_error` and the message "This job's stored launch plan could not be read. Start the work again." before any T3 call (a guarded transition, so it is in the feed and in matching webhooks, and the jobs behind it still dispatch in that tick), and one that already has a thread is followed as usual. Its views leave out what only the spec said: `projectName` and `model` are null, and so is `workspaceMode`. Append-only migration 11 (after the webhook migrations 9 and 10) advances the ledger version without changing data or schema; older builds reject that ledger before their old parser, which reads any spec it does not know as no spec, can mistake v2 scratch plans for legacy worktree jobs. Stop older processes before upgrading and use a pre-upgrade ledger backup if a downgrade is needed. Existing idle and standing jobs continue from their recorded host/thread even after an alias is removed.

Job views expose additive `workspaceMode` (`scratch`, `worktree`, `root` on a host that chooses workspaces, or null for an adopted standing thread, or a job whose stored launch plan cannot be read, with unknown workspace). The existing string `branch` stays empty for scratch. `fleet_status` exposes host `defaultProject` and alias `workspaceMode`; `fleet_projects` includes workspace mode and null worktree fields for scratch aliases. Scratch footers preserve the original task first and describe T3 internal scratch without claiming a branch. Every launched title keeps the final `[job:<id>]` marker and the caller's meaningful title.

### Workspace selection

Optional per host (`hosts[].workspaceProbeCommand`; operator reference in [configuration.md](configuration.md#workspace-probe)). Without it everything above is unchanged: no spec for an alias-only job, version 1 specs for targets and selections, `startFromOrigin: false`, the legacy request-id hash and no downstream call until dispatch.

With it, a named-project `work_start` records a **version 3 launch spec**: the project (id and name only when the request had to read T3's catalog; an alias-only request records neither and is resolved at dispatch through the alias), runtime mode, model and the **intent**: `auto`, `root`, or `worktree` with the base ref (`baseRef` is the alias's, or the discovery policy's, captured at acceptance; an explicit `worktree.baseRef` overrides) and `startFromOrigin`. The intent lives only in the spec. A request that names no workspace keeps its legacy request-id hash; one that does hashes the canonical `workspace` too, so changing it under a request id conflicts. Acceptance reads nothing from T3 or the host, so alias-only starts queue while the host is down. Explicit `workspace` on a host without a probe, or for a scratch alias, is `invalid_argument` and creates nothing.

At dispatch, after the existing checks (host, access ceiling, alias still maps to the project and accepts work, runtime mode, model), the engine reads the project's folder from T3 and runs the probe (`src/jobs/workspace.ts`: fixed argv, no shell, JSON on stdin, 15 s, 16 KiB, stderr discarded, killed on shutdown). The inspection is never stored: the outcome (`root` or `worktree`) and a hash of host plus canonical folder are written with the claim (`jobs.workspace_kind`, `jobs.workspace_root_key`, migration 12), and `t3_thread_launch` gets `workspaceStrategy: { type: "root" }` or the worktree form with `startFromOrigin`. A root job's `branch` is emptied. Specs of version 1 and 2 never probe, whatever the host's current config.

Failure isolation: a probe failure fails or defers only its own job. The ledger query that picks candidates (`JobStore.queued`) leaves out, in SQL, jobs whose probe asked to wait (`probe_retry_at`) and root jobs whose folder another job holds, so neither fills the window; the dispatcher looks at free slots plus a small margin, over a few rounds, with at most eight probes per host per tick. T3 host failures still propagate to the host backoff. A malformed stored spec is the PR15 `launchSpecUnreadable` path: that job fails, nothing else.

**Root reservations.** `jobs.workspace_root_held_at` is the reservation, owned by the job row; a partial unique index on `(host_id, workspace_root_key)` where it is set makes a second holder impossible, and the dispatch claim (`JobStore.dispatch`) and `reserveRoot` check and set it inside one immediate transaction. The key is a hash of host plus the canonical path the probe reports: the reservation is per identical path, so nested paths (a repository root and a subdirectory) are not related to each other, and jobs there are not serialized. `JobStore.#write` keeps it in step with every state or delegated-work change: held while the job is in a slot-holding state, or idle with delegated work; released on terminal, queued and plain idle. A watcher observation of work started in T3 itself takes the reservation if free and otherwise records the overlap (`workspace_root_contended`, code only); gateway-initiated starts and resumes are the ones that are enforced. Standing jobs, work started in T3 itself and a message T3 processes after the grace period are outside the guarantee.

Resume ownership: resuming an idle root job (`work_continue`, `work_respond`) calls `reserveRoot` before the T3 call. Each attempt adds an opaque random token to `jobs.workspace_resume_tokens` (a JSON array in the job row, the one owner of this state; never shown or logged) and sets `workspace_root_held_at` to now, so every attempt, a retry included, restarts the ten-minute grace period. The attempt that T3 definitely did not take (`T3ToolError`, or a transport failure that delivered nothing) calls `abandonResume(token)`, which removes only its own token; the folder is returned only when no token is left and the job is at rest. An attempt whose outcome is unknown keeps its token, so the uncertainty survives a restart and a later definite failure of a retry cannot free the folder under it. A successful call settles only its own operation (including deduplicated retries) after recording its running or question state; state changes never settle sibling attempts still awaiting a response. A cancelled job likewise retains unresolved attempts until their individual settlement or the grace sweep. `releaseStaleHolds` clears holds and tokens older than the grace period for idle or terminal jobs with nothing delegated, which is safe for the original send because a send is never retried by the client and is bounded by the call timeout.

### Reconciliation

- `unknown` and stale `dispatching` jobs (including after a restart) are reconciled by searching the project's threads for the marker (`t3_thread_search` or `t3_thread_list` with `projectId`). Found: attach the thread and continue. Not found for a configured window with the host reachable: `failed` with reason `launch_not_confirmed`. Never relaunch automatically; the agent may start a new request.

### Watching

- The watcher polls active jobs every `pollSeconds` with `t3_thread_read` (incremental; its messages view for replies and state, its activity view for delegated work) and `t3_pending_request` (`action: "list"`). It derives the state, records the latest assistant message excerpt and activity time, and emits events on change.
- On startup, the watcher resumes every non-terminal job.
- Unreachable hosts: back off, record `hostUnreachableSince`, keep the job's state.

### Follow-ups, responses, cancel

- `work_continue`: `t3_thread_send` to the job thread; idempotent on `requestId` (stored).
- `work_respond`: `t3_pending_request` (`action: "respond"`) for a pending request id belonging to the job's thread only.
- `work_cancel`: `t3_thread_interrupt`; `cancel_requested` until the watcher sees the thread stop, then `cancelled`. A queued job cancels immediately without contacting T3.

### Thread settlement

`work_settle({ jobId, requestId })` needs Operate on the job's host, like `work_continue` and `work_cancel`; any authorized operator client can settle the job, not only its creator. It accepts `idle`, `cancelled`, `failed` and `released` jobs with a thread. It reads current thread/run state in the messages view, then scans the activity view for active delegated work, including on terminal jobs the watcher no longer follows. The scan is bounded to 20 pages of 100 items; an incomplete scan fails closed with `job_state_conflict` and asks the client to settle in T3. A stale ledger cannot bypass the fresh check. T3's own settlement command provides the final guard against running turns, queued user messages and blocking approvals/questions; its known lifecycle refusals map to `job_state_conflict`.

The gateway calls `t3_thread_organize` with `action: "settle"` using the existing host credential, with no enrollment, permission change or fallback credential. Capability denial or a target above the credential's runtime/interaction ceiling returns `t3_unauthorized` with fixed guidance to ask the operator to review access. HTTP credential rejection keeps the existing `t3_unauthorized` behavior. Other failures retain their normal typed errors.

Settlement clears the pin, ends PR watches and detaches provider sessions; it leaves archive state unchanged and does not change the gateway job state. T3 cancels queued automatic notification/delegation wakeups and message-answerable async questions rather than queued user work. See [static contract verification](evidence/thread-settlement.md). The gateway reads `settled` and `settledAt` after the mutation; it reports success only when `settled` is true. The confirmation and one `thread_settled` feed event commit atomically. This event does not add a webhook event type.

Request ids are scoped to client and tool. Authorization precedes replay; a completed request returns its original confirmation without another T3 call, even if the thread has since resumed. `work_status` reads settlement live; null means no thread, unsupported metadata or an unavailable read, never an inferred false. Settlement is not cached in dashboard snapshots and needs no migration. Unlike sends, organize has no downstream retry key: after a crash or an ambiguous response the gateway only reads back, never re-sends for that request id. If still unconfirmed it returns `t3_response_lost`; inspect `work_status` and use a new request id only for a new settlement. Definite permission/lifecycle rejection or non-delivery releases the key for retry. An unrecognized tool error retains the key because it may follow side effects.

`work_continue` on a settled **idle** job is allowed: T3 accepts the new message, clears settlement and resumes the thread. Cancelled, failed and released jobs remain terminal and cannot be continued. There is no `work_unsettle` tool; starting another turn already handles the common resume case. Fresh reads cannot make the delegated-work check and T3 mutation atomic; T3's own final guard covers running/queued work, while the delegated check reflects the completed scan.

### As built

This section records how the job layer behaves in detail, including where it differs from or refines the plan above. Code: `src/jobs/` (store, service, engine, derive, interrupt) and `src/mcp/workTools.ts`.

**Engine.** One loop (`JobEngine`) ticks every `watcher.pollSeconds`, and at once after `work_start`, `work_continue`, `work_respond` and `work_cancel`. Ticks never overlap. Per host with open jobs, a tick runs, in order: reconciliation, watching, dispatch. Hosts are processed in parallel.

**Events.** Every state change appends a `state_changed` event (`fromState`, `toState`, and a `reason` such as `launched`, `reconciled`, `completed`, `question`, `approval`, `followup`, `input_answered`, `interrupted`, `launch_rejected`, `launch_not_started`, `launch_not_confirmed`, `run_failed`, `released`, `turn_started` (an idle job running again without `work_continue`: a person typed in T3, or T3 resumed a coordinator whose delegated work finished), `waiting_on_delegated_work` (a turn ended while work the thread delegated still runs)). The first event of a job is `created` (reason `adopted` for a standing job, in its first state). Events that are not state changes: `followup_sent` (a follow-up steered into or queued behind an active turn), `input_answered` (with the T3 request id), `turn_finished` (an idle job ran a whole turn it did not get from `work_continue` between two reads: started from T3 itself, or a coordinator resumed by T3), `delegated_work_ended` (reason `no_turn_started`: an idle job's delegated work ended and no turn followed; see "Delegated work"), `interrupt_requested` (work_cancel on a standing job), `thread_settled` (a confirmed work_settle, without a job state change). Event details hold gateway-generated reasons and codes only, never content.

**Starting.** Job ids are 10 lowercase Crockford base32 characters (safe in branch names, titles and search). The thread title is the agent's `title` (optional, at most 80 characters) or the task's first non-empty line, cut to 60 characters, followed by ` [job:<id>]`. Anything shaped like a marker (`[job:…]`, any case or spacing) is removed from the agent's text first, so a title cannot carry another job's marker. For a worktree job, the task (at most 20,000 characters) is sent with the footer `Started through t3-fleet-gateway as job <id>, in a fresh worktree on branch <branch>.` Request ids are scoped to the calling agent and the tool (`idempotency_keys` is keyed by client, tool and request id), so an id used with `work_start` and again with `work_continue` names two separate requests. The input hash covers the project, task and title.

**Standing instructions.** There is no pre-existing configurable task preamble; the dispatcher extends the existing `launchMessage` formatter with optional global `standingInstructions` (trimmed, 1–4,000 characters). A labelled `<operator-standing-instructions>` block precedes the caller task, so the worker reads shared operator context first; the existing footer follows unchanged. Global scope covers aliases, discovery and scratch uniformly without override precedence. The caller-only hash, stored task and title stay unchanged. Unset preserves launch bytes. Dispatch uses the currently loaded config (including queued jobs after restart), not a per-job snapshot. With the 20,000-character task bound and footer this stays below T3's 120,000-character message limit. Follow-ups are unchanged because the initial block is already in the thread; adopting a standing job reads existing history without injecting a message, and its follow-ups are unchanged too. T3-originated turns are outside this feature. Text is private prompt content and is never logged or included in diagnostics.

**Launch retry keys.** A session advertising `t3_thread_launch.clientRequestId` receives `t3fg-launch-<jobId>` on every launch. The client repeats one transport failure, including timeout, with identical input and key. A reconnect must still advertise the key and use the original authorization credential before a retry is sent; a transport failure or refusal of the retry cannot erase the first attempt’s uncertainty. Legacy hosts receive no new launch field. Remaining ambiguity and crash recovery still use marker reconciliation, never a rebuilt launch. Plain follow-up keys remain job/client/request-derived, with a private credential digest and attempt count durably bound in the existing idempotency response before sending. Replays require the same identity; older uncertain sends without that metadata fail closed for inspection. The digest is never tool output, an event detail or a log field. A definite first failure releases only its own unshared claim; later refusals preserve earlier uncertainty; attachment follow-ups still have no upstream key and keep their durable uncertainty guard. See [upstream contracts and limits](evidence/launch-retries-model-search.md).

**Dispatch.** Slots: `dispatching`, `running`, `needs_input`, `cancel_requested` and `unknown` hold one; `idle` does not, so a host may start its next queued job while an idle job waits for review, and `work_continue` on an idle job does not wait for a slot. Queued jobs dispatch oldest first. Before launching, the engine makes one read-only call (`t3_environment_read`): after T3 restarts, the first write on a dead keep-alive connection fails with a reset that is indistinguishable from a lost response, and a read can safely absorb it. Project titles are resolved to ids with `t3_project_list` once per process. Launch outcomes:

| T3 client outcome | Job |
| --- | --- |
| Result | `running`, with the thread id and run id |
| Tool error (`isError`) with a code T3 returns before creating anything: `invalid_request` (for example no model selection where the T3 project has no default), `target_required`, `capability_denied`, `project_not_found` | `failed`, `lastError.code` = T3's code |
| Any other tool error | T3's own guidance is to look before retrying after an error, so the engine looks for the marker once (as in reconciliation). Found: the job continues on that thread (`reconciled`), or fails with `launch_not_started` if no run started on it (see Reconciliation). Not found: `failed` with T3's code. The lookup fails in any way, a T3 error included: `unknown`, with T3's launch error as `lastError`, and reconciliation decides (failing the job would free its slot while a thread may exist) |
| Transport failure, `delivery: not_delivered` | back to `queued`; the host is backed off |
| Timeout (`t3_timeout`, after 60 seconds) | `unknown`; no further launches this tick, and the host is not backed off: T3 prepares the worktree before answering, so a slow launch says nothing about the host (the next tick's probe does) |
| Other transport failure with `delivery: unknown`, or an unexpected result shape | `unknown`; the host is backed off if it was a transport failure |

**T3 delivery classification** (`T3TransportError.delivery`, `src/t3/client.ts`). `not_delivered`: any failure while connecting or initializing the MCP session, a refused or unresolvable connection (`ECONNREFUSED`, `ENOTFOUND`, `EAI_AGAIN`, `EHOSTUNREACH`, `ENETUNREACH`, `EADDRNOTAVAIL`, `UND_ERR_CONNECT_TIMEOUT`), `401`/`403` (`t3_unauthorized`), and other `4xx` answers (`host_unreachable`). `unknown`: a timeout after the request was sent (`t3_timeout`), a reset or closed socket, or a `5xx` answer (`t3_response_lost`). A `404` (T3 forgot the session) is retried once on a new session; read-only calls are also retried once after `host_unreachable` or `t3_response_lost`. A T3 `isError` result on a launch is not taken as proof that nothing was created (see the launch outcomes above).

**Reconciliation.** A `dispatching` job that this process is not launching (after a crash or restart) becomes `unknown` (reason `dispatch_interrupted`). For each `unknown` job, and each `cancel_requested` job without a thread, the engine looks for the marker with `t3_thread_list { projectId, titleContains: "[job:<id>]" }` (unsettled threads, T3's default), then the same with `settled: true` (a person may already have settled the thread), then with `t3_thread_search { projectId, query: <id> }` confirmed by reading each match's title; a match T3 refuses to read (a T3 tool error) is skipped, so one unreadable thread cannot stall reconciliation, while host failures still abort the lookup. A thread counts only if its title ends with the marker (after trimming); a title that merely mentions it belongs to some other thread. Found: the thread is attached (`running`, or interrupted if the job was cancelled meanwhile). A found thread on which no run ever started (no `latestRunId`, and a thread status that is not active) never received the task, so instead of `running` (which the watcher would turn into `idle`, "turn finished") the job becomes `failed` with `launch_not_started` (`cancelled` if a cancel was requested), keeping the thread id and link; the message names the launch's own error code, if any. Live, T3 left no thread behind after an `invalid_request` refusal, but a launch that failed or timed out later may. Not found: the window starts at the first miss and counts only while the host answers; when the host becomes unreachable the window restarts. After `reconcileWindowMinutes` the job fails with `launch_not_confirmed` (a cancelled one becomes `cancelled`). The window start is kept in memory, so a restart restarts it: conservative, never sooner. Nothing is relaunched.

**Watching and state derivation** (`src/jobs/derive.ts`). For each job with a thread in `running`, `needs_input` or `cancel_requested` (every tick) or `idle` (at most once a minute), the engine calls `t3_thread_read { threadId, view: "messages", afterPosition, limit: 100, runLimit: 5, maxCharsPerItem: 2000 }`, following `nextPosition` for up to 5 pages, then `t3_pending_request { action: "list", threadId }`, then reads the activity view for delegated work (see "Two views, two read positions" below). It relies on these output fields: `thread.status`, `thread.activeRunId`, `thread.latestRunId`, `thread.pendingRequestCount`, `thread.updatedAt`, `recentRuns[].runId` and `.status`, `items[].position`, `.itemId`, `.type`, `.createdBy`, `.creationSource`, `.status`, `.text`, `.title`, `.updatedAt`, `nextPosition` and `hasMore`. The job keeps `lastRunId`: the run returned by `t3_thread_launch` or `t3_thread_send`, and the thread's `latestRunId` once a turn is over. Rules, first match wins:

1. A `cancel_requested` job becomes `cancelled` when nothing is active (rule 3 does not hold); otherwise the interrupt is sent for the run that is active now (`thread.activeRunId`, else `thread.latestRunId`), with that run's `clientRequestId`: a repeat for the same run is deduplicated by T3, and a run that started after the cancel (a queued follow-up, or a person typing in T3) is interrupted too.
2. `needs_input` when `t3_pending_request` (`action: "list"`) returns ids, or a run is active and `pendingRequestCount` > 0. A thread or run being `waiting` alone does not establish a permission request: real Codex can briefly report it with a zero count after an answer. With no listed question ids, it is a permission approval (`waitingForApproval` in `work_status`, reason `approval`).
3. `running` when `thread.activeRunId` is set, `thread.status` is `preparing`, `queued`, `starting`, `running` or `waiting`, or the followed run (`lastRunId` in `recentRuns`) has one of those statuses. A status this build does not know counts as active.
4. `failed` (`lastError.code` `t3_run_failed`) when the latest run's status, or the thread's, is `failed`.
5. Otherwise `idle`: the turn is over (`completed`, `interrupted`, `cancelled`, `rolled_back`, or `idle`). A turn stopped from T3 by a person is therefore `idle`, not `cancelled`: the thread can take the next instruction. The reason is `waiting_on_delegated_work` when the thread still has delegated work running (below).

An idle job that the watcher sees running again was not continued through the gateway (`work_continue` moves the job to `running` itself), so that `state_changed` has reason `turn_started`. When a whole such turn happens between two reads of an idle job (idle jobs are read once a minute), the job stays `idle` and the event is `turn_finished`, recognised by a new `latestRunId`.

The excerpt is the newest settled worker message among the items of the messages-view read, cut to 2,000 characters; activity-view items are never considered. `jobs.latest_message_truncated` (schema migration 6, `excerptTruncated` in `work_status`) records whether it stops short of the message (T3's `textTruncated`, or a longer text); agents read the whole message with `work_messages` (below). Migration 6 marks excerpts stored before it as cut when they are 1,999 or 2,000 characters long. A worker message is an item not created by a user, whose `type` does not mention `user`, and whose `type` mentions `assistant` or `plan`, or mentions `message` with `creationSource` `provider`. Messages the gateway or a person sent are excluded (T3 records the launch prompt and follow-ups as `user_message` items created by `agent` through `mcp`), and so is other activity such as `command_execution` or `checkpoint` items. A live read of a finished turn (thread `completed`, `activeRunId` null, latest run `completed`; items `user_message`, `command_execution`, `assistant_message`, `checkpoint`) is a test case in `test/jobs-derive.test.ts`. `subagent` and `notification` items (no creator, no creation source) are not in the messages view, and would not be worker messages if they were, so neither a child's task prompt or summary nor T3's notice that it finished is taken for the coordinator's reply. The read position is T3's `nextPosition` in the messages view (`afterPosition` is exclusive; T3 returns the last returned item's position), stored as an integer (`jobs.read_position INTEGER`); it never moves past a worker message whose status is `pending`, `running` or `waiting`, so a message still being streamed is read again once settled. No other item holds it (before round I a pending command or delegated work held it, which could hide every newer reply).

**Two views, two read positions** (`src/jobs/activity.ts`). `t3_thread_read` has two views over the same positions: `messages` (T3's default) returns only user messages, assistant messages and proposed plans; `activity` returns every timeline item, including `reasoning`, `dynamic_tool`, `command_execution`, `checkpoint`, `subagent` and `notification` items. Live, over the same range of a coordinator thread, the activity view returned `reasoning`, `dynamic_tool` (the delegate call), the `subagent` item (`status` `running`), the parent's `assistant_message` and another `dynamic_tool`, while the messages view returned only the `assistant_message`. So the excerpt, the state and `jobs.read_position` come from the messages view (few items, exactly the replies), and delegated work from the activity view, with its own position, `jobs.activity_position` (schema migration 4), so a busy coordinator's reasoning and tool items never slow the messages read. Every watched job, launched ones included (a launched worker can delegate as well), reads after the messages read and the pending-request list: `t3_thread_read { threadId, view: "activity", afterPosition: activity_position, limit: 100, runLimit: 1, maxCharsPerItem: 1 }`, following `nextPosition` for up to 10 pages (1,000 items; a longer burst is caught up over the next ticks). One character per item is enough: a `subagent` item's title is a field of its own, and its text is never used. The messages read goes first because a `subagent` item comes before the reply that mentions it, so the later activity read sees the delegated work behind any finished turn the messages read saw. Nothing holds the activity position back: delegated work still running is followed by item id (below), not re-read in place. A quiet tick is therefore two reads (one per view), plus one activity read per cluster of followed tasks the activity position has passed. Any new `t3_thread_read` must name its view (`T3Client.readThread` requires it).

**Delegated work** (`jobs.delegated_work`). Observed live from a T3 coordinator: when it delegates, its own run completes while the child thread works; the child appears in the parent's timeline only as one `subagent` item (`createdBy` and `creationSource` null, `title` the child's task title, `text` the child's task prompt while it runs and its final summary once done), in the activity view only; when the child finishes, T3 appends a `notification` item to the parent and starts a new parent run by itself. The watcher follows every `subagent` item the activity read returns with an active status (`pending`, `running`, `waiting`, `queued`, `starting`, `preparing`) by item id, position and title (titles cut to 200 characters), the first 200 by position. Running tasks beyond those are counted, not followed (`jobs.delegated_untracked`, schema migration 5, shown as `delegatedTasksUntracked`), so a job is never reported free while children it does not follow may run: while the count is above 0 the job waits on delegated work, until a turn that started after the last of them were counted has finished (`jobs.delegated_untracked_run_id` holds the thread's run at that time; the count is cleared when the turn that ends is a later run). Each tick, followed items the activity read did not return (the activity position has passed them) are read again in the activity view from the earliest one's position and matched by item id (`limit` 100, `maxCharsPerItem` 1, at most 5 reads); one T3 shows settled, or no longer has, is dropped. (T3 can also read one item by `itemId`; live, it answers an item it does not have with no items rather than an error, but one read per followed task would cost more reads than the cluster read.) Job views report `waitingOnDelegatedWork` (any followed, or any counted beyond those), `delegatedTasks` (their titles) and `delegatedTasksUntracked`; the attention reason then says `following <n> of <total> delegated tasks; ask the coordinator for status before sending more work`. Live, T3 showed a `subagent` item as `running` while its child worked and `completed` (with the summary) once it finished, and returned `title` and `status` in full with `maxCharsPerItem: 1`; so the flag is what agents act on, and the idle state meaning, the attention reasons and the `work_continue`, `work_feed` and `work_status` descriptions say it wins over the reply text when they disagree. When an idle job's delegated work has all ended (finished, failed or cancelled) and no turn followed in the same read (T3 starts one by itself when a child finishes, but not for every ending), the watcher appends `delegated_work_ended` (reason `no_turn_started`) and records the time (`jobs.delegated_ended_at`, cleared when the job changes state or another turn finishes); the job's attention reason becomes "Its delegated work has ended (finished, failed or cancelled) but it did not resume. Send work_continue asking it to check on that work." A job that finishes (`cancelled`, `failed`, `released`) follows no delegated work: the list and the count are cleared with the transition. T3 output statuses are parsed as strings so a new T3 status does not break watching. A T3 tool error naming a missing thread (`*not_found*`) fails the job (`thread_missing`), or cancels it if a cancel was requested; other tool errors are recorded on the job and retried next tick. An observation is written only if the job is still in the state it was read in, so an agent action that lands while T3 is being read (a follow-up, an answer, a cancel) is never overwritten by stale data.

**Failures that concern one job.** A T3 tool error or an answer in an unexpected shape (`t3_invalid_response`) while reconciling, watching or interrupting one job is recorded on that job (`lastError`, logged as `jobs.reconcile_failed`, `jobs.watch_failed` or `jobs.interrupt_failed` with the job id); the job keeps its state and is tried again next tick, and the other jobs on the host are reconciled, watched and dispatched in the same tick. A failed lookup is not a miss: it neither starts nor advances the reconciliation window. Should anything else escape one step of a host's tick (reconcile, watch, dispatch), it is logged (`jobs.host_tick_failed` with the step) and the next step still runs.

**Hosts.** A transport failure on a host aborts that host's tick, marks it unreachable (`hostUnreachableSince` on all its open jobs, which bumps their `updatedAt`, as clearing the mark does; `jobs.host_unreachable` logged once) and backs it off: `pollSeconds` doubling per failure, at most 5 minutes. The next attempt starts with `t3_environment_read`; success clears the mark. Job states never change because a host is unreachable.

**Follow-ups.** `work_continue` accepts `idle`, `running` and `needs_input` jobs. It claims the request id before calling `t3_thread_send { threadId, message, mode: "auto", clientRequestId }`, where `clientRequestId` is derived from the job, the agent and its request id. A delivered request is answered from the stored result (`replayed: true`). A failure with `delivery: unknown` keeps the claim, and the agent is told to repeat the call with the same request id: the gateway sends again with the same `clientRequestId`, which T3 deduplicates. A tool error or `not_delivered` failure releases a first, unshared claim; after an earlier uncertain attempt the claim remains. An idle job moves to `running`; otherwise a `followup_sent` event records the delivery (`steered` or `queued`).

**Pending-request compatibility.** T3 0.1.3 and nightlies from `0.1.3-nightly.20261027.3748` combine the three pending-request tools into `t3_pending_request` with `action: "list" | "read" | "respond"`. T3 0.1.2 and older nightlies use `t3_pending_request_list`, `t3_pending_request_read` and `t3_pending_request_respond`; both contracts are supported. Before any pending action, the client walks `tools/list` (at most 32 pages, 1,024 tools per page and 4,096 total names; duplicate names and repeated cursors fail closed). Discovery is shared and cached per host MCP session, refreshed on reconnect or credential change, and failed discovery is not cached. The combined tool is preferred whenever advertised, otherwise all three legacy tools must exist. Selection happens on the session that sends the call, including a safe HTTP 404 retry after a forgotten session. No tool failure, timeout, lost response or malformed result triggers a resend under another tool name; discovery fails before sending an answer. Advertised input/output schemas are ignored by the runtime adapter, which continues to decode results with its own parsers. Compact advertised schemas therefore do not change runtime decoding. Observations keep the legacy per-action labels for consistent dashboard diagnostics. The other consolidated tools (queue, transfer, configuration and schedule updates) are not gateway dependencies.

**Responses.** `t3_pending_request` (`action: "list"`) covers user questions only, and `t3_pending_request` (`action: "respond"`) "cannot approve a permission request"; T3's MCP tools offer no way to answer approvals. `work_respond` therefore answers questions only: it lists the job thread's pending ids live and refuses any other id (so a request of another job's thread is refused), then passes `answers` through to T3 unchanged (an object, at most 16,000 characters of JSON). `work_status` reads pending requests live (`t3_pending_request` with `action: "read"`, up to 5 by default, 5-second timeout per read); optional `pendingRequestId` selects any listed request instead. T3-owned pending request IDs are opaque non-empty strings passed through unchanged; real Codex IDs exceed 200 characters, so neither response nor targeted-read inputs apply a gateway-invented length cap. Both structured output and text carry question ids, headers/text, all option labels/descriptions/values, and `multiSelect`, `allowCustomAnswer` and `required`. Null or absent flags become null (unspecified); the gateway does not invent defaults. Text explains option-value/label fallback, arrays for multi-select, optional versus required answers, custom-answer permissions and the 50-answer/200-character question-id/16,000-character answers-JSON constraints. Requests exceeding 50 questions, 100 options per question or 64,000 serialized JSON characters return no partial questions: `questions` is null with `questionsUnavailable: "too_large"` and an operator-in-T3 path. Other null results carry `read_limit` (select `pendingRequestId`) or `temporarily_unreadable` (T3 returned null or the read failed; retry without inventing answers). Question data stays live and is never stored in events or logs. `work_feed` directs question handling to `work_status`; `work_cancel` does too when an interrupt leaves a question pending. Approvals are reported as `waitingForApproval`, and the operator gives them in T3. This is a deviation from the plan's "approval decision or question answer".

Unspecified flags alone do not block an answer or require escalation: text directs the agent to follow explicit question wording. Without instructions to select several, a single listed value (or its label when no value is supplied) is a conservative answer attempt, not an asserted T3 default. T3 validation is authoritative. No request-retention guarantee is made on rejection, and uncertain delivery must not be retried blindly. Public text-only tests cover omitted and null flags; a live Codex test confirmed a real single listed label answer when T3 omitted those flags. Other providers, multi-select/custom answers and rejected-answer retention remain unconfirmed live.

**Cancel.** `queued` → `cancelled` without T3. `cancelled` and `failed` are reported as they are. A job without a thread yet (launch in flight or unconfirmed) becomes `cancel_requested` at once. For a job with a thread, the gateway reads it (`t3_thread_read { threadId, limit: 1, runLimit: 1 }`) to learn the active run and calls `t3_thread_interrupt { threadId, clientRequestId: "t3fg-cancel-<id>-<runId>" }` (`runId` is `activeRunId`, else `latestRunId`, else `none`). The key is per run, not per job: T3 deduplicates by `clientRequestId`, so one key per job would turn every interrupt after the first into a no-op. `runId` is not passed to T3, so a status other than `interrupt_requested` keeps meaning that nothing is running on the thread. Then the job is recorded: `interrupt_requested` makes it `cancel_requested` until rule 1 confirms; any other status (`no_active_run`, `completed`, `interrupted`, …) means nothing runs, so the job is `cancelled` at once (an idle job cancels this way). If T3 cannot be reached, the job becomes `cancel_requested` and the watcher delivers the interrupt. A job cancelled while its launch is in flight or unconfirmed is interrupted as soon as its thread is known, and cancelled outright if the launch is rejected, never reached T3, or is not confirmed in the window. A T3 tool error on the interrupt is returned to the agent and the state is kept.

**Feed.** Agents persist `nextCursor` after processing a page and retain it together with their OAuth token store across ingress loss/restarts; reconnect with saved credentials, refresh if needed, then read strictly after that cursor. Reuse request ids and identical input for uncertain idempotent mutations. Gateway auth does not restart disabled connector routines; tested SDK limits and unverified Grok/Notion behavior are in [operations.md](operations.md#authentication-and-outage-recovery). `work_feed` returns events with ids greater than the cursor (default 0), oldest first, `limit` default 50 and at most 200, plus `nextCursor` (the last returned id, or the given cursor) and `hasMore`. `attention` lists, most recent state change first and at most 50: `needs_input` and `unknown` jobs of any age, and jobs that became `idle` or `failed` within the last 24 hours (`jobs.state_changed_at`, shown as `stateChangedAt`, set only when the state changes), or whose delegated work ended while idle within the last 24 hours (`jobs.delegated_ended_at`; ordered by the later of the two). Every job view also has `updatedAt`, the last time any field changed: writes that change nothing, such as the watcher reading an unchanged thread again, are skipped, so it never just means "last polled". There is no acknowledgement state; an idle job leaves the list when it is continued, cancelled or 24 hours old. `mine: true` limits events and attention (and `work_list`) to jobs the calling agent started and every standing job: no agent starts a standing job, but agents drive it as their own, and leaving it out hid the coordinator from an agent filtering with `mine`.

**Worker messages** (`src/jobs/messages.ts`, `work_messages`). The excerpt is bounded, and feed events carry codes only, so an agent reads a reply in full with `work_messages`, which reads T3 at call time and stores nothing. It returns worker messages only (as for the excerpt: never the task, follow-ups or a person's messages, never activity items or delegated work summaries), oldest first, with `position`, `type`, `status`, `text` (at most `maxChars`, default and at most 50,000, T3's `maxCharsPerItem` ceiling), `textTruncated` and `length` (the full length when the text is complete, null when cut: T3 reports no full length). Without `before` or `after` it returns the latest `limit` messages (default 1, at most 10); `earlier` is the `before` for older ones (null when there are none) and `later` the `after` for newer ones, never past a message still being written, so reading on returns it again once settled. T3 reads only forward, so the gateway scans the messages view with one character per item: forward from the job's `read_position` to the end, then back in windows of 100 positions, one read each (positions are unique integers, so a read of 100 items covers its window), at most 20 reads each way per call (2,000 positions back; a later call continues from `earlier`). Then it reads each chosen message by `itemId` with `maxCharsPerItem` set to `maxChars`; T3 answers an item it does not have with no items (confirmed live, as is `textOffset` continuing a cut text), and such a message is left out. The tool's text summary carries the messages too, for clients that read only text content. Like the excerpt, the text is never logged.

**Links.** T3 may supply an environment-scoped autolink, `<t3-thread://v2/<environmentId>/<threadId>>`. The client schemas unwrap autolinks and older markdown links into bare target URLs, preferring a usable supplied link so v2 keeps the owning environment. Both v2 segments use the shared thread-id character allowlist and 2,048-character bound; empty segments, extra path segments, URL delimiters, malformed percent escapes and dot paths (including percent-encoded dots) are refused. V2 ids otherwise stay as written, including opaque percent escapes, as in [upstream's parser](https://github.com/pingdotgg/t3code/blob/c2fbf0a5/packages/shared/src/threadLinks.ts). Bare and markdown v1 links remain supported. An absent, null or unusable link falls back to `t3-thread://v1/<threadId>` using the shared canonical builder (colon delimiters preserved, literal percent signs and URI/Markdown punctuation escaped); an id that cannot form a safe link gives null. Legacy HTTP(S) links remain usable in job views, but never in the dashboard or webhooks. The launch result (or, for a reconciled launch, the thread list or read that found the thread; failing those, the first watcher read) stores the target URL (`jobs.t3_thread_link`), and every job view returns it as `link`, null until then. A job's existing stored link is retained. Dashboard and webhook links prefer a validated stored v1/v2 URL and otherwise use the canonical builder. A successful watcher observation clears a prior `t3_invalid_response` error; malformed responses still fail validation and keep the error. Links are never logged.

**Standing jobs.** A standing job is an existing T3 thread the operator registers so agents can drive it with the same tools, for example a long-running coordinator ("chief of staff") thread the operator created and works in. Only the operator CLI creates one, so an agent cannot attach itself to arbitrary threads. Code: `JobService.adopt` and `release` (`src/jobs/service.ts`), `JobStore.adopt`.

- `jobs adopt <project> <threadId> [--title <text>]` reads the thread through the project's host (`t3_thread_read`, then `t3_pending_request` (`action: "list"`)) and refuses it unless `thread.projectId` is the project's T3 project; a thread T3 does not know is `not_found`. The job is stored with `standing = 1`, client id `operator` (so `startedByYou` is false for every agent; `mine` filters include standing jobs anyway, see "Feed"), request id `adopted`, no task, the given title or else the thread's T3 title (no marker), the thread's branch and link, and a first state from `observe` over that read (`running`, `needs_input` or `idle`). The read position is the thread's current end: the adoption reads the messages view in pages of 100 (at most 1,000 pages; the watcher catches up on anything longer) and keeps T3's last `nextPosition`, stopping before a message that may still change as the watcher does, so history is not replayed and the excerpt starts as the thread's latest worker message. The activity position is the thread's current activity end, read in the activity view from the last message's position (positions are shared, so the tail after the last message is short), and delegated work still running is found by a bounded scan backwards from that message: one activity read per 100 positions, `maxCharsPerItem` 1, at most 20 reads in all, of which the tail takes at most 15, so at least 5 always look back from the message (where a coordinator waiting on delegated work has it). Delegated work further back is not found; a tail longer than 15 reads leaves the activity position short of the end, and the watcher catches up (and finds delegated work in the rest of the tail then). A standing job without an activity position (adopted before migration 4) gets the same scan, from its read position, on its first check. `lastRunId` is the active run, else the latest. The first event is `created` with reason `adopted`.
- Adopting a thread an open standing job of the same project follows returns that job (`created: false`, without calling T3); a thread any other open job follows is refused (`job_state_conflict`). Once released, a thread can be adopted again as a new job.
- Never launched or reconciled, and never in `queued`, `dispatching`, `unknown` or `cancel_requested`. Standing jobs hold no concurrency slot in any state (`slotHolders` and `fleet_status`'s `runningJobs` leave them out): they are a person's long-lived thread, and counting a coordinator that runs for hours would block the launches it may itself be waiting for.
- Watched like any job with a thread: `running`, `needs_input` every tick, `idle` once a minute, with the same derivation. A coordinator that delegated is `idle` while its children work (its own run has completed), waiting on that work as described under "Delegated work", and `running` again when T3 resumes it; child threads are not jobs. The attention entry for an idle standing job that waits on nothing says to read its reply, that nothing it delegated is still running (the flag wins over the reply text), and to use `work_continue` when the reply asks for input or the work is done. Like launched jobs, a failed run leaves a standing job `idle` (reason `run_failed`, `lastError.code` `t3_run_failed`); the error clears when a later turn is observed. A thread T3 no longer has still fails the job (`thread_missing`).
- `work_continue` and `work_respond` work exactly as for launched jobs. `work_cancel` interrupts the current turn only: the gateway reads the thread, and if a run is active, calls `t3_thread_interrupt` with the per-run key and appends `interrupt_requested` (outcome `interrupt_requested`, `confirmed: false`); the job keeps its state until the watcher sees the run stop and makes it `idle`. If nothing is active, no interrupt is sent (T3 would answer a repeat for an already stopped run from its record of the first interrupt) and the outcome is `not_running`, with `pendingQuestions`: the question ids T3 still lists for the thread (`t3_pending_request` (`action: "list"`)). Interrupting does not necessarily withdraw a question: if T3 keeps listing it after the run stopped, the job stays `needs_input` (rule 2) until an agent answers with `work_respond` or the operator dismisses it in T3, and repeating `work_cancel` says so rather than reporting the job stopped; once T3 lists none, the stopped thread is `idle`. Whether T3 keeps a question after an interrupt is not confirmed live; the fake can do either (`keepQuestionsOnInterrupt`). The turn interrupted may be one the operator started in the T3 app, which the `work_cancel` description says. Nothing is deferred: a transport failure is returned with advice to repeat the call, which reuses the run's key.
- A project with `allowWorkStart: false` refuses `work_start` (`start_disabled`), so agents go through its standing jobs. The setting only gates new requests: jobs already queued when it was turned off still dispatch. `fleet_status` lists every project's open standing jobs, and the `fleet_status`, `work_start` and `work_continue` descriptions tell an agent to talk to a project's coordinator with `work_continue` and follow it with `work_feed` and `work_status`.
- `jobs release <jobId>` moves a standing job from any open state to `released` (reason `released`) without calling T3: the thread, and any run on it, carry on. The engine stops watching it. A job the gateway launched cannot be released (`invalid_argument`); agents cancel those.

**Not stored in the database.** Backoff state, the reconciliation window start and idle poll times are in memory and restart conservatively; entries of finished jobs are dropped at the end of each tick. Catalog snapshots (below) are in memory too.

### Discovery

`fleet_projects` retains archived projects and exposes `pinned` and `archived` from T3's optional `pinnedAt`/`archivedAt` metadata (null when an older host omits them). Archived rows carry explicit guidance to check with the operator before new work. These organization flags do not override configured launch policy or change alias resolution; hiding a row could remove an alias match and accidentally apply the discovery policy instead.

Opt-in per host (`hosts[].discovery`, see "Configuration and data"), off by default. Existing worktree aliases keep their downstream-free queueing path. Explicit scratch aliases resolve their pinned id from a fresh project list even with discovery off; targets, catalog browsing and explicit model selections require discovery. Code: `src/hosts/catalog.ts` (snapshots, bounds, cursors), `src/mcp/catalogTools.ts` (`fleet_projects`, `fleet_models`), `src/jobs/targets.ts` (how a T3 project maps to configured aliases and which policy governs a launch), `src/jobs/launchSpec.ts` (model selection validation and the recorded launch spec), `JobService.start`, and the spec path of `JobEngine` dispatch.

**Authorization first.** Both catalog tools and `work_start` authorize the host before the registry, cache or T3 are touched and before any metadata or error about the host is produced: an explicit host the agent may not read, or that is not configured, is a generic `not_found` (`No host "<id>"`); a hostless call reads only the hosts the grant covers; a cursor for a hidden host is refused the same way. A target on a host the agent may read but not operate is `insufficient_scope`. Existing read and operate grants, fleet-wide or per host, apply unchanged.

**Catalogs** (`CatalogService`). Per host, two catalogs read from T3 on demand only, never on a timer: projects (`t3_project_list`, up to 20 pages of 100; more, or a cursor that repeats or does not advance, makes the whole catalog unavailable: `catalog_limit` or `t3_invalid_response`, never a partial list) and models (`orchestrator_capabilities`, bounded to 100 providers, 2,000 models, 64 option descriptors per model, 256 choices per descriptor and 1,000,000 characters of sanitized JSON, else `catalog_limit`). A completed read is sanitized into a whitelisted snapshot (projects: id, name, whether T3 has a default model; models: provider instance id, driver kind, display name, runtime modes, `canRunChildTask`, `canRunCrossProviderChildTask`, constraints, and per model id, label and option descriptors with id, label, description, type, choices and current value; never workspace paths, scripts or other project settings) and answers for 30 seconds; concurrent readers share one in-flight read; `refresh: true` reads again; a failed read is reported to its callers (`available: false` with the error code, per host, never hiding the other hosts) and replaces nothing. Every snapshot carries a random id (96 bits, new for every read; never a per-process counter, which would start again at 1 after a restart and let an old cursor page a new snapshot). Page cursors (`fleet_projects`, `fleet_models`; 50 items per host per page by default, at most 100) encode the tool, host, snapshot id and offset: a cursor pages the snapshot it was issued for, however old, and is refused once that snapshot was replaced (by a refresh, the TTL, or a restart, whether or not the new process has read since), so a page never mixes two reads or repeats an item. A cursor needs its host and cannot be combined with `refresh`; hostless calls return each readable host's first page.

`fleet_models` accepts optional `search` (trimmed, nonempty, at most 200 characters). On supporting sessions it passes the query to `orchestrator_capabilities`; older sessions still receive `{}`. Each provider reports `omittedModels` (0 when absent upstream). Upstream returns a short default list and at most eight search matches per provider, not an exhaustive catalog; narrow the query to find other visible models. Hidden models remain hidden. `total` and cursors cover only returned models. Each host holds one model snapshot/query; a changed query replaces it, concurrent identical queries share a read, and cursor calls must repeat the query. Explicit selections search the requested model id in a fresh catalog at acceptance and dispatch, preserving exact option validation. See [source evidence and limitations](evidence/launch-retries-model-search.md).

Model options accept both full descriptors (`id`, `label`, `type`, `options`, `currentValue`) and T3's compact MCP descriptors (`id`, `values`, optional `default`; introduced by upstream [PR #22889](https://github.com/pingdotgg/t3code/pull/22889)). String values become select choice ids; boolean values become a toggle. Missing labels fall back to displayName, name or id. Missing types are inferred from choices or boolean values/defaults; otherwise the option is skipped. Unknown explicit types remain listed but not selectable. Empty compact values lists are malformed and skipped. Malformed models and options are isolated with fixed warning events containing only host ids and counts. Raw collection limits still fail the whole catalog with `catalog_limit`. Explicit selections must match the normalized advertised model, option and choice ids at acceptance and dispatch.

**Launch policy for a T3 project** (`src/jobs/targets.ts`). From a project snapshot, each T3 project is mapped to the host's configured aliases: an alias with `t3ProjectId` maps to that id; an alias with `t3ProjectTitle` maps to the single project with that title, or, when several projects share the title, marks each of them ambiguous. Then: exactly one alias → the alias governs (`allowWorkStart`, `workspaceMode`, `runtimeMode`, `baseRef`, `branchPrefix`, model defaults, standing-job guidance, the job's `project` is the alias); several aliases or an ambiguous title mapping → `invalid_argument`, the agent must name the alias; no alias → the host's `discovery` policy, and `discovery.allowWorkStart` false is `start_disabled` naming the aliases that do accept work. `fleet_projects` reports exactly this per project (`launch.allowed`, `source`, `alias`, `aliases`, `runtimeMode`, `workspaceMode`, `baseRef`, `branchPrefix`, `defaultModelSource`) with a guidance line. Targeting by id therefore never circumvents a configured project, and a configured `allowWorkStart: false` stays uncircumventable.

**`work_start` with a target or a model selection.** Exactly one of `project` (alias) or `target: { host, projectId? }` (host-only uses the scratch default described above); optional `modelSelection: { instanceId, model, options?: Record<string, string | boolean> }` (at most 32 options and 16 KiB). Both objects are strict: a field the gateway does not know (`reasoningEffort` beside `options`, say) is refused by the input schema with no job, never dropped, so a job is never started without an option the agent asked for. The request id is first looked up in the requesting client's ledger. For an existing key, the job's stored host must still permit Operate access before the job is read or any replay result or conflict is returned. Otherwise the result is a generic `insufficient_scope` without job or host metadata. An authorized replay compares the hash of the original input and returns the recorded job without resolving the current alias, host default or catalog, even if the alias was removed, renamed or moved. An alias-only request without a selection hashes exactly as before this feature, so earlier request ids replay. A request with a target or selection hashes its canonical target and selection with option keys sorted, so reordered options replay and a changed target, model or option conflicts with `request_id_conflict`. For a new key, the requested host is authorized before any registry or catalog read or metadata disclosure. An alias-only worktree request without a selection is recorded at once and resolved at dispatch, exactly as before (`launch_spec` null). Scratch aliases resolve and record v2 specs as described above. A target or explicit selection needs `discovery.enabled` (`discovery_disabled`), the project list is read from the host now (never from the browse cache: the policy follows project titles, and a project renamed after an agent browsed must not be classified from the old snapshot; a host that cannot answer fails the request with that error and nothing is resolved from an older read) and the policy above applied, and an explicit selection is validated against the host's capabilities read fresh: provider instance and model must be advertised, each option id must be a `select` or `boolean` descriptor of that model, a `select` value one of its choice ids, a `boolean` value a boolean (`false` preserved); anything else is `invalid_argument` naming what is available, and no job exists. Without a selection the whole configured default applies (project, then host, then T3's project default; for a discovered project the host default, then T3's default, else `invalid_argument` asking for a selection) with no merging of options across levels. The job is then created in one transaction (the duplicate check runs again inside it, after the awaits) with `t3_project_id` already set and a `launch_spec` (worktrees retain migration 8's v1 format: `{ v: 1, projectId, projectName, source: alias | discovered, alias, baseRef, runtimeMode, model: { source: explicit | project | host | t3_default, selection } }`); a discovered job's `project_alias` is the internal ref `@<host>/<projectId>`, which is outside the alias syntax and needs no config entry. Job views (`work_start`, `work_list`, `work_status`, `work_feed` attention) add `projectId`, `projectName`, `source`, `model` and `workspaceMode`; feed events add `host` and `projectId`; `work_list` filters by `target` in SQL before its limit, and `project` accepts the internal ref.

**Dispatch of a job with a launch spec.** The engine launches from the spec: project id, workspace (`baseRef` for worktrees) and the exact model selection it recorded, never from the current catalog or a re-resolution. Right before the launch it reads the host's project list again and checks that the recorded policy still holds: for an alias job, the alias still resolves to the recorded project (a title may have moved to another project) and still accepts work; for a discovered job, no configured alias maps to the project and the host still allows discovery launches. For every job, with or without a spec, the runtime mode it will launch with must still be within the host's access ceiling and no broader than the alias's or the host's discovery `runtimeMode` now (a job recorded under a narrower mode keeps it). Otherwise the job fails before any launch with `launch_policy_changed` (a project that is gone: `project_not_found`), so a project renamed into a configured title while the job was queued is never launched under the discovery policy. An explicit selection is validated once more against the host's capabilities read right before the launch: a host that cannot answer either read leaves the job `queued` (the host failure backs the host off as usual); a selection the host no longer advertises fails the job before any launch (`lastError.code` and event code `model_selection_invalid`); `catalog_limit` fails it too. A spec whose alias is no longer configured fails with `project_not_configured`, as an alias-only job would. A stored spec this build cannot read fails the job with `database_error` before any of these reads, and is never launched as an alias job. Everything after the launch call is unchanged: lost responses are `unknown` and reconciled by the marker in the recorded project, never relaunched; cancel, idempotent mutations and the watcher work the same. T3's `invalid_request` for a missing model carries a hint to pass `modelSelection` or set the host default. `canRunChildTask` is never used to decide whether a launch may happen; it is returned as metadata only.

**Privacy.** Catalog content (project names, model and option ids, choices, constraints) is returned to authorized agents and never logged or put in event details; `test/logging.test.ts` and `test/discovery.test.ts` check this. The launch spec stores ids, names and the selection, no task text.

### External thread discovery and adoption

T3 v0.1.6 excludes side chats from project thread lists and search, even with subagents included. Its MCP read/detail omits `lineage.sideChat`, so a fork read alone cannot establish eligibility. Client adoption and adopted-job resume require a fresh, bounded thread catalog containing that fork; missing or incomplete listings fail closed. Ordinary listed forks remain eligible, including on older hosts. The watcher only follows existing ledger thread ids: it does not discover or import side chats. Operator standing-job adoption remains an explicit choice. See [v0.1.6 source verification](evidence/t3-v0.1.6.md).

`fleet_threads { host, projectId, limit?, cursor?, refresh? }` requires **threads:read** plus Read on that host. `work_adopt { host, projectId, threadId, requestId }` requires **both threads:read and threads:control** plus Operate on that host. Discovery must be enabled for listing and new adoption; no new config setting is introduced. Unknown/unreadable hosts remain generic `not_found`, authorized before any catalog/registry read. Projects are validated against the host's project catalog; new adoption uses a fresh read and verifies the thread's actual project. A unique configured alias is retained; ambiguous mappings are refused; an unconfigured project uses `@<host>/<projectId>`. `allowWorkStart` controls launches, not adoption: adoption never launches, so it may import a thread from a coordinator-only or unconfigured project. It preserves the thread's runtime/model/workspace. Before a continue or answer on an adopted job, a fresh thread/project read checks membership, lineage and the current alias (or discovered-project) runtime ceiling plus the host ceiling. Unknown modes and broader modes fail closed without sending; stopping/settling keeps the existing T3 checks. Adoption itself can still import such a thread for observation.

Listing defaults to 50 entries, maximum 100. It returns `threadId`, a control-character-free title bounded to 200 characters, T3 state, `lastActivityAt` (T3's `updatedAt`, including metadata changes), nullable settlement/archive fields, and `gatewayOwned`, `jobId`, `origin`. `gatewayOwned` means a gateway launch, while the job fields also identify standing/adopted records, including terminal history. Ownership is joined from the current ledger on every page. A per-host/project snapshot holds only whitelisted metadata for 30 seconds; simultaneous readers share in-flight work. `refresh` replaces it. Opaque cursors bind host, project and random snapshot ID; replacement, restart or eviction refuses a cursor. There are at most 32 cached project snapshots, 20 upstream pages of 100 threads per snapshot and a 1,000,000-character sanitized text budget. Oversize catalogs fail with `catalog_limit`. Malformed entries are skipped with one content-free warning per completed scan (host id and bounded count only). Duplicate ids retain the newest valid `updatedAt`, with a lexical comparison of sanitized metadata breaking equal-time ties; unknown timestamps sort below known ones. Raw entry counts drive upstream cursor/completeness checks, while the returned total counts valid distinct threads. Invalid page envelopes, nonadvancing cursors or visibly changing totals still fail with `t3_invalid_response`. Upstream offset pages are live rather than atomic, so unchanged totals cannot prove a perfectly simultaneous snapshot. There is no timer or dashboard external-thread catalog route.

Thread inputs and catalog/link decisions share one server/browser validator: 1–2,048 ASCII characters from letters, digits, `._:!~*'()-` and complete `%HH` escapes, excluding the dot path segments `.` and `..`. This includes T3's UUID, MCP, derived provider/delegation and imported id forms. Raw slashes, whitespace, controls and query/fragment delimiters are refused at those boundaries. T3 responses and MCP job output instead accept bounded opaque ids (nonblank, at most 2,048 characters, no controls); an unfamiliar format still launches, reconciles, reads, sends and interrupts, but its generated link is null and discovery skips it. The upstream brand itself only requires a nonblank string. Canonical app links preserve colon delimiters, leaving `mcp:<uuid>` links byte-identical, and escape literal percent signs plus URI/Markdown punctuation; decoding once recovers the exact id. The [source evidence](evidence/thread-catalog.md) documents upstream formats and link handling. No thread id is used as a filesystem path or HTTP route; SQL binds it as a value, cursors contain snapshot ids and offsets, and dashboard text uses DOM text APIs. Control logs identify the job instead of a possibly path-bearing provider thread id; durable action audits retain the id as bound SQL data.

Adoption shares the standing-job observation, watcher and controls. Migration 14 adds `origin` (`gateway`, operator `standing`, client `adopted`), `adopted_by`, `adopted_at`; existing standing rows are backfilled from their operator/creation metadata. `standing = 1` remains the lifecycle flag for both forms: no launch/reconciliation or concurrency slot, failed/interrupted turns become `idle`, pending questions become `needs_input`, active/unknown T3 statuses are treated conservatively, and delegated work is tracked through the activity view. Message history is read in the messages view and remains available through `work_messages`. No task text, launch spec, root reservation or model change is fabricated for an import. Archived and app-owned subagent threads cannot be adopted. Client imports/resumes require known archive and lineage metadata; missing or unfamiliar values fail closed with `t3_invalid_response`, while ordinary reads remain compatible.

Adoption itself makes only read-only T3 calls. A transaction owns the job and request key: per-client `work_adopt` request IDs reject different input; the same host/thread returns the same adopted record even with another request ID/client. A gateway-launched job, including finished jobs and launch markers whose response is not yet reconciled, or an operator standing job, cannot be imported as a client adoption. Thread identity includes its host. A released adoption stays released on replay or repeated adoption: the operator can use `jobs adopt` to deliberately register it again as a standing job. `jobs release <jobId>` stops following without contacting T3. `work_cancel` interrupts only the active turn, never closes the imported job. Continue/respond/settle retain their existing fresh checks, retry keys and ambiguous-write rules; control attempts and replays are audited with client, host, thread, job, action and time, never their content. Adoption's initial audit is atomic with the job/event/request key. Private dashboard settlement uses its existing guarded operator route, and imported jobs show `adopted` instead of `standing`.

Thread scopes are **operator-only client opt-ins**, absent from OAuth defaults and advertised metadata. Migration 14 creates an initially empty `client_thread_scopes` table. Every access-token verification combines its original host grant with that client's current thread opt-ins; it neither rewrites nor reissues tokens, refresh families, hashes or expiry. Scope edits serialize through SQLite and take effect on the next request in the running process; already authorized in-flight operations may finish. Refresh rotation/narrowing changes the original host grant only; it cannot add thread opt-ins or restore removed ones. The opt-in applies to all otherwise valid tokens for the chosen client, including later OAuth grants, until removed. Revoked/expired tokens remain unusable. No existing client is opted in and no wildcard/all-client grant command is provided.

```sh
t3-fleet-gateway clients list
t3-fleet-gateway clients grant <clientId> --scope threads:read --scope threads:control
t3-fleet-gateway clients scopes <clientId>
t3-fleet-gateway clients ungrant <clientId> --scope threads:control --scope threads:read
```

`clients grant` and `clients ungrant` require at least one `--scope`, are idempotent, validate the entire scope list before writing, reject unknown clients/scopes, and append content-free `operator_scope_events` audit rows even for no-op retries (removal is recorded as action `revoke`). Only the two thread scopes can be changed this way; host grants stay unchanged. `clients revoke <clientId>` keeps its whole-client revocation meaning and rejects `--scope` with a usage error pointing to `clients ungrant`. `clients list` shows ID, name, base access, effective scopes, created/last-used times, status and sign-in origins, never secrets/hashes; `clients scopes` shows one client's effective union and its thread opt-ins. Distinguish similarly named connectors by a known request's `mcp.tool_call.clientId` and `clients diagnose` success timestamps; these identify server-side use, not which token/sibling a connector saved.

Only client-imported jobs (`origin: adopted`) need `threads:read` for reads and `threads:control` for mutations in addition to their host grant. Operator-registered standing jobs (`origin: standing`) retain exactly their existing host Read/Operate authorization: they remain in `fleet_status.standingJobs`, `work_list`, `work_feed` and disabled-start hints, and work with the existing read/control tools without either thread scope. Clients without read opt-in receive `insufficient_scope` on direct adopted-job reads and have only adopted rows removed in SQL before limits in `work_list`/`work_feed`; `fleet_status` and `start_disabled` omit only adopted metadata. Thread discovery and client adoption still require their explicit thread scopes, even when the caller can operate standing jobs. The private dashboard remains an operator surface with its own network boundary and exposes no external catalog through the public MCP listener.

**Verified upstream contract and limits.** Checked [T3 main at 3b95e783](https://github.com/pingdotgg/t3code/blob/3b95e7831b11b17627dff16843bc087bfca397ec/packages/contracts/src/orchestratorMcp.ts) and [nightly v0.1.2-nightly.20261021.3499 at b5a226e4](https://github.com/pingdotgg/t3code/blob/b5a226e49c52ecab4ddc2d678a7012d97e651a6a/packages/contracts/src/orchestratorMcp.ts); these contracts match. This is source qualification, not a live gateway/T3 deployment test.

- `t3_thread_list` takes `projectId`, `statuses`, `titleContains`, `settled`, `snoozed`, `includeSubagents`, numeric cursor and limit up to 100. List items include IDs, title, run status, latest run, creation/update times, settlement/snooze and lineage. Omitted `settled` includes both shelves in current T3. The [service](https://github.com/pingdotgg/t3code/blob/b5a226e49c52ecab4ddc2d678a7012d97e651a6a/apps/server/src/orchestration-v2/ThreadManagementService.ts) reads active-location shells and orders by `updatedAt` descending, excluding archived/deleted threads; the list has no archive flag or archive enumeration input. Gateway discovery excludes subagents explicitly. Missing archive/settlement fields on older hosts stay null, never inferred false. There is no dedicated last-message activity timestamp.
- `t3_thread_read` reads another existing thread by ID with `messages`/`activity` views, shared positions, `itemId`/`textOffset`, and at most 50,000 characters per item. `work_messages` keeps its existing bounded retrieval. Thread detail includes archived/settled, runtime mode and lineage, so adoption can refuse archived/subagent targets by ID. Deleted threads are not readable.
- `t3_thread_send` follows up with `auto`, `queue`, `steer` or `restart` and `clientRequestId`; the gateway keeps `auto` and its existing stable retry key. This sends a follow-up, not a special empty Resume action. `t3_pending_request` (or the legacy list/read/respond tools) supports user questions, **not permission approvals**. An approval stays an operator action in T3.
- `t3_thread_interrupt` supports active-run interruption and `clientRequestId`; it does not delete/close the thread. `t3_thread_organize { action: "settle" }` settles, with no request key. The gateway retains quiet-thread/delegation checks and confirmation reads, and never retries an ambiguous settlement blindly. Hosts missing settlement metadata fail confirmation gracefully.
- [T3 PR #22889](https://github.com/pingdotgg/t3code/pull/22889) shortened model catalogs and compacted options to `{ id, values, default }`, with `search` for omitted models. Current gateway normalization already handles those descriptors. This change does not configure/substitute models when adopting and does not pretend the default advertised model list is complete.

## Outbound job webhooks

v0.1.9, issue #18. Connections are managed by the operator through the private dashboard or `webhooks.subscriptions` configuration; no connection exists by default. `src/webhooks/config.ts` validates routes and private auth files; `store.ts` owns subscription revisions, immutable pending payloads, delivery leases and bounded diagnostics; `sender.ts` owns POST transport and its independent timer; the management module owns dashboard input validation, synthetic tests and mutations. There is no inbound webhook endpoint or destination-management MCP tool. Owner-only notification tools use operator-provisioned connections. Keeping capture synchronous in the ledger transaction avoids the crash gap of a post-commit callback; a network call inside that transaction would block normal work, so the sender reads the outbox independently.

**Atomic capture.** Migration 9 appends `job_turns`, `webhook_subscriptions`, `webhook_deliveries` and `webhook_attempts`; it leaves old jobs, events and feed IDs intact and creates no historical deliveries. `JobStore.#insertEvent` captures matching event-time job fields and enqueues one immutable JSON payload per matching subscription in the same transaction as the job and append-only source event. The source maps `state_changed` into `needs_input`, `idle`, `failed`, `cancelled` and optional `running`; `turn_finished` maps to `idle` (an entire turn between polls), and `delegated_work_ended` keeps its name. Adoption's `created` is not a transition notification. All deliveries for one source event share a new UUID `eventId`. A watcher observation checks its original job snapshot, writes changes and same-state events together; this closes the former crash gap between updating idle state/read positions and appending `turn_finished` or `delegated_work_ended`. `appendEvent` is transactional too. Event details remain code-only.

**Payload and attribution.** The flat payload is `{eventId,type,timestamp,feedSequence,feedCursor,jobId,projectAlias,host,projectId,title,state,previousState,threadId,link,standing,waitingOnDelegatedWork,turnInitiator}`; nullable IDs/links remain null. A scratch job (a host-only start or a scratch alias) is captured like any other: `projectAlias` is the scratch alias, `host` its machine and `projectId` the pinned T3 project, known from the job's creation, and no payload carries a branch. `timestamp` is the source event time as ISO UTC. The link is canonical `t3-thread://v1/<threadId>`, never a legacy HTTP link with possible query secrets. `turnInitiator` is `{kind:"gateway",clientId}` only for an exact run ID proved by a successful launch or a send with delivery `started`. Those mappings are persisted in `job_turns`; a send's idempotency result, attribution and event commit together. Queued/steered sends do not relabel an existing run. Unknown/reconciled/adopted or other unseen runs report `{kind:"unknown",clientId:null}`, never an inferred operator or the job creator. No upstream field presently proves operator origin. By default the excerpt fields are absent; a per-subscription `excerptChars` opt-in includes at most 500 UTF-16 code units, preserving surrogate pairs, plus `excerptTruncated`. It never includes a task body, questions, delegated task text or full messages. Titles may originate in a task's first line. Arbitrary secrets in worker output cannot be generically redacted: metadata-only is the default and receivers must be trusted for any opted-in content.

**Subscription ownership and lifecycle.** Migration 10 labels each row as `config` or `dashboard`; existing rows default to `config`. Only `startGateway` reconciles config, and only config-owned rows: removing an entry never removes or disables a dashboard connection, and an ID ownership collision is refused. Reconciliation happens after reserving both the MCP and optional dashboard listeners and before accepting work or starting background tasks. Dashboard management refuses writes until that readiness succeeds. A bind failure leaves the serving process's route revisions and pending payloads untouched. `openServices`, including read-only CLI commands, never applies config. Enabled config routes require a valid private secret file; all configured secrets are validated before any route change. A missing, empty or invalid secret fails startup and closes the reserved listeners and services, without starting probes, renewal, the engine or sender. Each persisted identity covers URL, header/value, filters and excerpt policy; an unchanged identity preserves its revision and pending queue across restart. A new or re-enabled subscription receives only future events. Disable, removal or any identity change cancels old pending/sending rows and clears their payload, then uses a fresh random revision; nothing old can be sent to the new recipient. A request already on the wire cannot be recalled. Every capture reads the persisted subscription table, so concurrent CLI writers use the serving configuration. Matching combines paired targets and host/project/event filters with AND, and values within a filter with OR; an omitted host/project filter includes all. The sender runs independently of the number of configured routes, so the first dashboard connection works without a restart and persisted dashboard queues resume on startup.

**Dashboard management.** The operator supplies a URL, a full authentication header and one project. Configured aliases remain available without discovery; their configured host is captured with the alias. The private read API also reads the sanitized project catalog on demand from each enrolled host with discovery enabled, sharing the catalog cache. Each host has an independent available/unavailable status; a failed host does not discard the others. Discovered selections store an exact `{host, projectId}` pair in `settings.targets`, matching both alias jobs and direct-target jobs by their recorded T3 project ID. Multiple pairs are ORed, then combined with any legacy host/project/event filters using AND. Optional `clients` (original job creator), `jobs` and `events` filters further narrow a connection; dashboard setup accepts these as optional comma-separated lists. The header is split at the first colon, then its name and value are trimmed and validated under the existing transport-header policy. The connection uses the default job and credential events and `excerptChars: 0`. Creation and replacement test synthetic content through `postWebhook` outside the database transaction, with normal TLS validation, no redirects and the same 10-second deadline as deliveries. Only an accepted 2xx result permits activation; it proves receiver acceptance, not that the bot finished. Replacement can retain the saved URL or supply a new one, and always needs a new full header. A failed test leaves an existing route active. The store checks the expected revision after the awaited test before committing: a stale replacement or test cannot overwrite a newer change or resurrect a disconnected row. Disconnect cancels the old queue. Config-owned rows are visibly marked and cannot be replaced or disconnected in the UI.

Management requests carry a session identifier from the read API and a UUID request ID, reused for a retry. The session changes on restart and a bounded in-memory result cache prevents repeated submission from repeating a committed action; it holds no raw destination or authentication value. A session retains at most 128 operations without evicting older results. Once it is full and all operations have settled, a fresh GET rotates the session; retries from an old session fail with `session_expired` rather than replaying an old action. At most four network operations run at once. The gateway computes project picker options grouped by host, with a `label` on each option. The first configured alias represents each host and pinned project ID, suppressing other copies; selection values retain their existing alias or paired-target semantics. Labels use the alias, otherwise the T3 project name. Only labels that collide within one host get a project-ID suffix, starting at eight characters and extending to distinguish shared prefixes. Title-based aliases without a known ID keep their label while colliding discovered choices get the suffix. The dashboard renders these labels directly. Catalog reads retain the existing per-host page and text bounds; unavailable hosts are shown explicitly. No discovery timers are added. All operations and responses are bounded. The list computes each connection’s `displayName` at read time: a paired target uses the current configured alias matching both host and project ID, then the discovered T3 project name when available, then its project ID. Legacy project filters retain their aliases; multiple labels are comma-separated and an unfiltered connection is “All projects”. The dashboard renders this server-provided name without resolving names itself. Configuration changes take effect on gateway restart; no connection settings or revisions are rewritten. The list exposes only IDs, revisions, source, project display names, configured projects/hosts and safe test time/outcome/status; it never exports saved destinations or credentials. Shutdown rejects new writes, aborts and drains awaited management pings before SQLite closes, and does not rely on closing listener sockets to cancel async handlers.

**Transport and recovery.** A separate sender has four slots, refills each completed slot independently, and polls once a second for newly queued work. Refills yield to the event loop. An IMMEDIATE transaction claims due rows with unique leases, permitting only one in-flight request per subscription across database connections; a stalled destination cannot fill all four slots. Concurrent senders cannot normally claim the same row. There is no async work inside a ledger transaction. Each POST uses the immutable stored bytes and configured auth, validates normal TLS, follows no redirects, and has an absolute 10-second deadline across DNS, connection, headers and response body. Responses are discarded, with a 32 KiB body and 16 KiB header bound. Failures (including non-2xx and redirects) retry after 5 seconds, doubling to a five-minute cap, until the source event is one hour old. No new attempt starts once expired. Shutdown aborts in-flight requests and leaves them retryable. An abandoned lease expires after 30 seconds (longer than the attempt deadline), records `abandoned` and becomes eligible again; an ambiguous acknowledgement can produce a duplicate. Failed bookkeeping also frees its local sender slot while leaving the lease for recovery. Completed, expired and cancelled payloads are cleared. `webhooks ping <id>` uses the same transport and auth with a synthetic UUID/timestamp and null feed cursor, never a job; it can validate a disabled or not-yet-applied config without applying it.

**Bounds and diagnostics.** At most 32 subscriptions across config and dashboard ownership, 10,000 active deliveries per subscription, and 16 KiB per JSON payload. Oversized upstream metadata is refused as a whole, never by truncating an opaque ID. A full queue never evicts active deliveries or rolls back a job: new matching events are counted in persistent `overflow_count`, with the last omitted feed sequence/time and fixed `overflow_reason` (`backlog` or `payload_limit`), exposed by `webhooks list`. Feed catch-up is required after overflow; delivery expiry also requires catch-up. No active row is pruned. Terminal metadata keeps the last 1,000 deliveries globally; attempts keep the last 100 per subscription and 1,000 globally, excluding currently running attempts from deletion. `webhooks attempts <id> --limit N` returns at most 100 attempts: subscription/event ID, attempt time, HTTP status or null, fixed outcome only. No URL, header name/value, payload, response body or raw network error appears. Private route/auth material is stored in the existing protected database, with no new encryption layer; backups remain secret.

**Feed compatibility.** `feedSequence` is exactly `job_events.id`; `feedCursor` is its decimal string, the unchanged public `work_feed` cursor representation. Notifications are filtered and may arrive out of order. Receivers deduplicate UUIDs separately, correlate feed IDs, and keep polling/catch-up from the last contiguous saved `work_feed.nextCursor` for their authorized feed. They must never set that cursor to the maximum webhook sequence or discard unseen lower sequences. A snapshot describes its event time, not the latest job state; read `work_status`/`work_messages` through the ordinary grant before acting.

Migration 15 is a data-free schema-version barrier for paired webhook targets. It changes no existing subscription settings, enabled/disabled configuration, route/key, revision, pending delivery or diagnostic. Legacy alias-plus-host connections keep their exact matching behavior. New discovered connections are scoped to a host/project-ID pair. Older builds refuse the version-15 ledger rather than ignore that filter and broadcast a delivery; rollback to an older build requires restoring a pre-upgrade database backup (and loses subsequent ledger changes). No re-registration or key rotation is required by the migration. Connect activates immediately after a successful synthetic test: there is no separate gateway “saved” or enable operation. Receiver-side routine activation and credential rotation remain receiver operations. A successful HTTP response proves endpoint acceptance, not routine execution.

### Precise notifications, health and replay

Connections keep their existing config/dashboard ownership and private receiver authentication. Optional
`jobs` and `clients` filters intersect existing hosts, aliases, paired targets and event filters; `clients`
means the client that originally started the job, independently of the current turn initiator.
An operator can pin `ownerClientId` and an explicit host ceiling on a config connection. That connection
sends only jobs its owner explicitly subscribes with `work_subscribe`, after starting work. MCP never
accepts a destination or credential. The bot must own the job and hold Operate on every connection host;
unknown and other-owner connections/jobs are indistinguishable. Each connection allows 100 job bindings.
An unsubscribe stops future capture; already captured events remain eligible for delivery/replay.
Operator-provisioned outbound authority persists independently of OAuth token lifetimes; remove or disable
the connection to revoke it. No bot may manage config/dashboard destinations or another client's jobs.

The ledger owns a bounded, immutable per-connection event archive (seven days, 10,000 events, 16 KiB each,
original payload bytes) in addition to the existing retry outbox. Capture and archive commit with the source event,
even when the pending queue is full. Replay uses original bytes and eventId, never today's job snapshot,
and runs against the current connection revision. Replacing a route cancels its queue and invalidates its
archive/bindings. Cursor/time replay scans at most 200 events per call, skips active duplicates, and resets
terminal deliveries with a fresh retry window. A persisted retention floor reports gaps; older history
requires authorized `work_feed` catch-up. Replay cannot recreate events predating the upgrade or connection.

Persistent per-connection last success, last failure, failure streak and expired-event totals survive
attempt-history pruning. Pending counts and retained replay bounds supplement these totals in the dashboard,
`doctor`, offline webhook diagnostics and owner-only `work_notifications`. Existing bounded attempt history,
one-hour exponential retries, delivery leases and shutdown behavior remain in force. Operator replay is a
local CLI operation (it queues work without sending or reconciling config); owner replay is an Operate MCP tool with the same host ceiling as subscription.

Migration 18 adds archive, bindings and health state without rewriting existing routes, revisions or pending
payloads. Health begins at upgrade; no historical success or event snapshots are invented. Stop all ledger
users and back up before upgrading. Older builds refuse the new schema; rollback requires restoring the
pre-upgrade backup and loses subsequent ledger changes. No version bump or live deployment is part of this work.

## Downstream T3 credentials

Per host, the gateway obtains a T3 MCP credential with T3's documented pairing-code approval, with no browser:

1. `POST {t3Url}/oauth/mcp/register` with a loopback redirect URI (`http://127.0.0.1:<unused-port>/callback`); the redirect is never followed. The client is named `t3-fleet-gateway (<host id>)`, which is the label T3 shows for the resulting session.
2. Run the host's `mintPairingCode` command (local `t3` CLI, or for a remote host, an operator-provided command such as `ssh other-host t3 auth pairing create …`) and parse `credential` from its JSON.
3. `POST {t3Url}/oauth/mcp/decision` with `{ authorization: {response_type, client_id, redirect_uri, code_challenge, code_challenge_method: "S256", state, resource}, decision: { _tag: "pairing-code", access, code } }`, read `redirectTo`, extract `code`.
4. `POST {t3Url}/oauth/mcp/token` (form-encoded, PKCE verifier, `resource = {t3Url}/mcp`). Store the access token and its expiry.
5. Verify with `t3_environment_read`, then switch over.

T3 issues no refresh tokens; credentials last 30 days. The renewal job re-enrolls when fewer than `renewWhenDaysLeft` days remain (or the credential has expired), keeps the old credential until the new one is verified, and reports failure in logs and `fleet_status`, with proactive credential alerts described below. It does not enroll hosts that were never enrolled; `serve` logs `host.not_enrolled` for those.

**Credential alerts and re-pair.** Automatic renewal and its preflight retain their existing timing and behavior. At each renewal check, persistent host alerts raise once for a failed attempt and once for each expiry threshold crossed (`renewal.alertDaysLeft`, default `[7, 2]`, one to eight integer days from 1 to 29; duplicates are ignored). Expiry thresholds are evaluated only while the most recent renewal attempt has failed. With the default five-day renewal window, the seven-day threshold first warns at the failed renewal, then the two-day threshold escalates if it remains unresolved. Healthy cycles, late successful checks and successful short-lived replacements emit no alerts. Repeated failures do not repeat an active alert, including across process restarts. Successful enrollment clears failure state and resolves the old credential's expiry warnings; successful replacements stay quiet until a later renewal failure. Removed thresholds resolve on the next check. Never-enrolled hosts are not automatically paired; an explicit failed initial enrollment still raises a failure alert.

Migration 19 adds `credential_alerts`, `credential_deliveries` and the read-only `notification_deliveries` union view. It changes no existing row or table. Alert state and its immutable outbox entries commit together. Verified credential installation, renewal success, old-alert resolution and notification capture also commit together, without network calls inside the transaction. A failed attempt is recorded before capture and is recoverable on the next check after an interrupted capture. The existing sender shares its concurrency, per-connection serialization, leases, retry window, queue budget, bounded attempts and persistent delivery health across both outboxes. Replacement/disconnect cancels both queues; late completions cannot revive them. Credential events have null job-feed cursors and are not in the job replay archive; inspect the current host alert state if their delivery window expires.

The credential payload is `{eventId,type,timestamp,feedSequence:null,feedCursor:null,host,reason,thresholdDays,expiresAt,alertId}`. `type` is `credential_alert` or `credential_resolved`; `reason` is `renewal_failed` or `expiry`; `thresholdDays` is null for failure, otherwise the crossed threshold; expiry is ISO UTC or null. `alertId` correlates a raise and its resolution; `eventId` identifies the immutable event across delivery retries. No error text, credentials, pairing codes, tokens, command data or catalogs enter these payloads. Local diagnostics retain a bounded stage/reason, HTTP status, recognized OAuth/T3 error or denial code, command exit code or executable-resolution code. The same safe format is logged and stored for enrollment and preflight; doctor and dashboard show it after validating stored values. Arbitrary upstream messages and unknown short codes can contain credentials, so they are excluded (unknown codes become `unrecognized`). Legacy raw stored messages fall back to fixed guidance. CLI enrollment uses these same safe diagnostics.

New connections include both credential event types by default. Existing connections retain their saved event selections, including file-managed routes that omit `events`: enable both events in configuration or the dashboard's **Replace key → Events** form, which tests the destination before changing its revision. The Webhooks page explicitly shows whether both events are enabled. All filters intersect. Host/project filters match a configured affected project or a recorded ledger job, with full host/project target pairs; unknown project membership fails closed. Job/client filters require a single affected job satisfying the complete intersection. Bot-owned routes additionally require that owner's matching job binding to include the credential events; there is no inferred host-wide bot ownership. Host alerts carry no task or job content.

The private dashboard shows active/resolved host alerts and Overview expiry warnings; `doctor` reads the same persisted state, including failed initial enrollment. **Re-pair** first prepares a bounded, five-minute, host-bound confirmation without minting anything. **Confirm re-pair** runs the existing configured pairing flow, probes the candidate with `t3_environment_read`, and atomically installs it only after verification. Failure retains the previous credential. Concurrent enrollment calls share one attempt; repeated confirmations replay the result for five minutes without minting again. A restart invalidates outstanding confirmations. These routes exist only on the private dashboard listener and require its existing Host/Funnel guards, custom API header, exact same-host Origin and same-origin fetch metadata when present, bounded JSON and ready-state gate. Shutdown rejects new actions and drains admitted repairs before closing SQLite. No pairing material is sent to or stored in the browser.

**Mint command preflight (v0.1.2).** `src/hosts/commandPreflight.ts` resolves the configured executable using the actual process environment (the same environment passed to the command runner); explicit paths use the current working directory, bare names use PATH, and absent PATH uses the Unix default. Missing/non-executable commands are failures; unverifiable filesystem checks are warnings. A selected `runtime/versions/<version>/` path warns; a stable symlink into that directory does not. Resolution alone does not verify wrapper internals, remote commands or versions.

Only an explicit `mintPairingCodeProbe` can be executed as preflight: the operator asserts that this exact argv is non-mutating. There is no automatic version probe, no guessed arguments for wrappers/SSH and no pairing flow. The existing `runCommand` injection gains an optional options argument (environment, timeout, output budget, abort signal); one-argument injected runners remain valid. Probes have a ten-second deadline (two seconds until 0.1.7: a launchd agent with ProcessType Background runs its children at a lower priority, and the configured T3 version probe, which answers in well under a second in the foreground, took over two seconds there on a test machine, so startup logged `probe_timeout` while foreground doctor passed; the deadline is a bound, not an expected duration, and HTTP startup does not wait on it), 4,096-byte stdout/stderr budgets and a bounded wait even if an injected runner ignores cancellation. The real runner retains its direct process and explicitly sends SIGKILL on abort, rather than relying on Node 26.0's SIGTERM-only `execFile` abort handler; the timeout also force-kills it. Probe exit failure/timeout/overflow is a failed check, success with no recognized version is warn/unverified, and version disagreement is diagnostic only. A bare stdout version, exact native `t3 v<semver>` output or JSON `{"version":"x.y.z"}` is compared to the T3 health version. Preflight uses only an already-completed, unexpired cached health result, never initiating or awaiting a health read; without one the comparison is explicitly unverified. Doctor supplies its freshly read health version. Only complete trimmed supported output is recognized, never embedded versions; neither raw output nor parsed probe versions leave the check. Diagnostics use fixed codes/messages, never argv, paths, output or thrown command error messages.

`doctor` includes these checks even for unenrolled hosts. `serve` checks in the background and starts renewal after every host check settles, even if a check unexpectedly rejects; that rejection logs only `host.pairing_preflight_failed` and the host id. Other diagnostics log host id and check code only; existing credentials continue serving through diagnostic failures. Logger sink errors still propagate. Before every automatic renewal, known executable resolution failures record `pairing_command_failed` without starting pairing registration. Probe failures are diagnostic and do not establish that minting would fail. Shutdown aborts the startup probe and prevents the renewal loop from starting afterward, without waiting for a probe or health read. No schema change is needed.

The T3 client keeps one MCP session per host, shared by every call to that host (watcher, dispatcher, health probes, agent actions). It replaces the session only after a session-level failure (a connection error or closed transport, a failure while connecting, `404` session lost, `401`/`403` or another `4xx`) or a credential change. A request timeout or a `5xx` answer fails only that call: closing the session would also fail every other call in flight on it, for example a launch whose response would then be lost. Each connection has a generation number, so a failure observed on an older connection never closes a newer one. A `404` (T3 forgot the session, so it never handled the call) is retried once on a new session. Other transport failures are retried once only for read-only tools; for state-changing tools a lost response is ambiguous, and the job layer must record it as `unknown` rather than retry. Old T3 sessions expire on their own; the operator can revoke them in T3's Settings → Connections.

CLI: `hosts enroll <id>`, `hosts status`.

This automates T3's consent step using the operator's own machine access (the same access needed to run `t3 auth pairing create`). Document this clearly.

## Operator dashboard

As built in v0.1.9 (`src/dashboard/`). An opt-in web view of the gateway for its operator: gateway, hosts, agent clients, jobs and recent job events, with manual **Run checks** and private **Webhook connections**. Webhook connection management and confirmed job settlement change state. Approvals, answers and interrupts stay in T3, and host credentials and client changes stay in the CLI on the gateway machine. Off by default (`dashboard.enabled`); with it off nothing below exists.

**A listener of its own.** `serve` starts a second HTTP listener on `dashboard.listen` (loopback only, default `127.0.0.1:3791`; config validation refuses the MCP port). Its router serves only the dashboard (`<basePath>/`, `<basePath>/assets/{app.js,app.css,mark.svg}`, `GET <basePath>/api/snapshot`, `POST <basePath>/api/checks`, `POST <basePath>/api/jobs/settle`, `GET <basePath>/api/webhooks`, `POST <basePath>/api/webhooks/{connect,replace,test,disconnect}`, and a redirect from `<basePath>` to `<basePath>/`); `/mcp`, `/oauth/*` and the metadata documents are `404` there. The MCP listener has no dashboard routes. So the tunnel that carries `/mcp` to agents (a public Funnel, say) cannot carry the dashboard unless it is pointed at the dashboard's port, and `doctor` and the dashboard's checks test exactly that through the real public URL (`src/dashboard/exposure.ts`): the public URL must not answer the snapshot route (`dashboard_public` / `dashboard_listener_public` fail). The intended publication is a tailnet-only reverse proxy on a path of its own (for example `tailscale serve --set-path <basePath> http://127.0.0.1:3791<basePath>`), with `basePath` equal to the proxy's mount path; page, assets and API use relative URLs.

**Trust boundary.** The network is the boundary: whoever can reach the dashboard listener (processes on the gateway machine, and devices the tailnet proxy admits) can read it, manage webhook destinations and settle jobs. There is no separate login, cookie or authentication token. The management session identifier limits request replay; it is not an access credential. Nothing is stored in browser storage. A pasted header exists only while entering/submitting the form and is cleared after submission or close; saved URLs and authentication values are never returned. Defenses against other origins: requests whose `Host` is not the listener's own loopback `host:port` (`127.0.0.1`, `localhost`, `[::1]`) or an exact `dashboard.allowedHosts` entry get `421` (DNS rebinding; a refused host is not echoed or logged); any request carrying `Tailscale-Funnel-Request` (Tailscale marks Funnel traffic with it) gets `403`; API requests need the header `x-t3fg-dashboard: 1` (a cross-origin page cannot send it without a CORS preflight, which is never granted), and are refused when `Sec-Fetch-Site` is present and not `same-origin` or when `Origin` is present and its host is not allowed; the checks POST also needs `application/json` and a body of at most 1 KiB. Webhook management POSTs additionally require a mandatory Origin matching the exact request Host, HTTPS except for a literal loopback host, `application/json`, and a body of at most 16 KiB; `same-site` fetch metadata is refused as well as `cross-site`. No CORS permission is granted. Every response has `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy` and `-Opener-Policy: same-origin`; the page and API are `no-store`. Refusals log `dashboard.request_refused` with a reason code only.

**Job settlement.** Quiet jobs with a thread (idle, failed, cancelled or released) offer **Settle** in Overview attention and Jobs rows, followed by **Confirm settle** / **Keep open**. `POST <basePath>/api/jobs/settle` accepts only `jobId` and `requestId`, with a 1 KiB JSON limit and the same API header, exact mandatory Origin, HTTPS/loopback and fetch-metadata guards as webhook writes. It is operator access through the existing private-network boundary, without a new bearer token, cookie or session. The handler calls `JobService.settle` as the operator with Operate scope; it never duplicates the MCP tool's settlement checks or changes a job's state. Writes are unavailable before readiness and during shutdown, and in-flight settlements drain before database close. The browser retains the request id after failure, preventing an uncertain retry from settling a newly resumed thread. Errors show fixed text and codes, including advice to check T3 when delegated work exceeds the bounded scan; no downstream error text is returned.

The durable `thread_settled` event acknowledges attention for dashboard reads only; Jobs retains the job, original state and history with a **settled** badge. Later job activity invalidates acknowledgement using event order, even with identical timestamps. PR-open/merge notifications alone do not invalidate it. Settling through `work_settle` has the same effect. This is an acknowledgement, not proof of task success or a permanent mirror of T3 settlement: external T3 changes need a subsequent gateway observation. No retry relationship is stored, repeated request ids identify the original job rather than a new attempt, and idle explicitly does not mean successful. Matching titles, task text or project plus a later merged PR cannot reliably establish that a failure was superseded. Automatic supersession is therefore intentionally omitted; failures remain visible until explicitly settled. Snapshot reads remain database-only.

**What a page load reads** (`buildSnapshot`, `src/dashboard/snapshot.ts`). The database and this process's memory only; it never contacts T3 or anything else:

- Gateway: version, start time, the MCP listener, the job engine's last tick (`JobEngine.status()`, in memory), schema version, and the last check run.
- Hosts: label, id, `t3Url`, the operator's `hosts[].transportNote` (descriptive, never checked), access ceiling, capacity (slot holders, queued, open, standing), discovery flags, the projects configured on it (alias, description, `runtimeMode`, `allowWorkStart`, whether the config sets the model, open and standing job counts). Reachability is the last completed host contact (`HostRegistry.lastHealth`, kept while another call is in flight) with its completion time, or `unchecked` before the first contact completes after startup. The central T3 client records successful calls, including catalog, project, thread, launch, settlement and interrupt calls; transport/timeout/auth failures update the same record. Auth rejection retains its distinct credential-rejected status. Enrollment and renewal record verified contact only after the new credential is committed; failed candidate verification leaves the installed credential's reachability unchanged. Application refusals and invalid payloads do not establish transport failure or recovery. A host the engine is backing off (in memory) and the earliest `hostUnreachableSince` on its open jobs are shown as such. Credential state and expiry; a renewal failure by code with a validated, bounded local diagnostic. Never the mint command, its argv, the probe or any other host setting.
- Host observations: `HostRegistry` owns a bounded, in-memory signal set per configured host (`src/hosts/signals.ts`). Completed model and project catalog fetches, individual supported T3 calls, work-start resolution after authorization, and pre-launch dispatch failures are observed. Each kind records the last result (`code: null` for success), fixed explanatory text (at most 300 characters), observation time, and an active problem's first/last times and saturating count. Error code changes retain the current episode's first time and count. A later completed success of that same kind clears its problem; cached answers and unrelated successes do not. Catalog success means the entire response passed normalization and bounds, not merely that T3 answered. Optional pull-request reads are excluded because older T3 versions need not support them. Start observations accept only host-side failures (transport, auth, protocol, catalog bounds, internal/database and workspace-probe codes); caller errors such as invalid models or missing projects neither create nor clear them. Per-call observations accept only transport/protocol/auth codes (`host_unreachable`, `t3_unauthorized`, `t3_timeout`, `t3_response_lost`, `t3_invalid_response`); thread-scoped application errors neither create nor clear them. Request validation and authorization refusals before host resolution are not host failures.
- Overview includes host attention cards using the same clipped configured labels as existing host cards, with code, fixed text, first seen, last seen and count, even when there are no jobs. Hosts shows the signal status and last model-catalog result/time; a missing observation says “not observed”. Credential/reachability failures retain their more specific status priority and suppress per-call cards with the same root-cause code; catalog/start/dispatch cards remain independent. A problem whose last occurrence is more than 24 hours old no longer contributes Overview attention or a red host status, but its last-seen history stays muted on Hosts. A recurrence makes it active again. Signals are process-local and reset on restart; times describe observations, not current availability. Snapshot reads remain downstream-free and attention retains its existing overall bound.
- Catalogs remain on demand, with no periodic refresh. This preserves the opt-in, authorization-before-discovery contract. Catalog failures are detected when agents call `fleet_models` or `work_start` with a model selection (and the catalog is fetched), covering failures encountered by those requests; a model problem requires an actual catalog fetch to be detected or cleared; an environment-only manual check cannot prove model-catalog health. We accept that detection gap rather than silently changing discovery into background monitoring. Failed fetches retain any older browse snapshot and their failure history; active attention follows the 24-hour rule above.

- Background reachability: `serve` schedules one `t3_environment_read {}` per configured, enrolled host 2–3 seconds after startup, then after each probe completes waits `reachability.intervalMinutes` (default 5, integer 1–60) plus 0–999 ms jitter. No host-level disabled setting exists; absent hosts and hosts without credentials are never contacted. Each probe has a five-second total deadline including MCP initialization, one attempt with no transport retry, and its own cancellable connection so shared work calls are unaffected. At most one probe per host is in flight; missed time is never queued. Failures wait for the next interval. Timers are unref'd; shutdown clears them, aborts and drains probes before storage closes, and cancellation does not create a host failure. Offline `openServices` commands and the synthetic dashboard demo do not start this loop. Probe results use the same reachability record and environment-call signal as manual checks; they never fetch or clear catalog health, change job state, enroll or renew credentials. Invalid intervals fail startup with `config_invalid`.

- Clients: each established client (an OAuth client with a grant family, or an operator token), at most 100, unrevoked first then by last use, from `ClientStore.list()` and `diagnoseClient` (the same offline diagnosis as `clients diagnose`): kind, the registered name and the operator's display name (`dashboard.clientLabels`, by client id), redirect origins, access, grant state, the latest expiry of usable access and refresh grants (`never` for a non-expiring operator token), revoked families with reason codes, and the observed success times (`last_mcp_success_at`, `last_refresh_success_at`, legacy `last_used_at`). A null success time is **unknown**, never inferred from other fields. Status is derived conservatively: no usable grant is `Needs new approval` / `Token unusable`; a usable grant never observed is `Never observed` (unknown, not connected); a success within a day is `Seen recently`; older is `Quiet`, which is normal for agents that call rarely. A usable grant is never presented as proof that the connector holds a working token. Access is what the gateway would accept now: the scopes of the client's usable access tokens and usable or grace-retry refresh tokens (`FamilyDiagnostic.currentScopes`), so a refresh that narrowed the scope, or a wider grant whose tokens expired, never counts; the approval's own scopes are shown apart (`access.approved`) only when they are wider. Registrations without an approval are listed apart (count and the 10 newest names), as untrusted text.
- Jobs: counts by state; open jobs (the newest 100, with the total), the 25 most recently created finished jobs, and the agent attention query (`JobStore.attention`, 24 hours). Per job: id, title (the agent's title or the task's first line, as T3 shows the thread, with the `[job:<id>]` marker removed), project (and, for a discovered-project job, its T3 project name from the launch spec; a scratch job is shown under its alias like any alias job, and no job shows a branch), host, state and times, who started it (client display name, or the operator for standing jobs), whether it waits for an approval or for questions (a count), how many delegated tasks it follows (a count, never their titles), host unreachability, its error code with fixed text, and a T3 link. The link is built as `t3-thread://v1/<threadId>` only when the thread id is made of `[A-Za-z0-9._:-]` (at most 200), never taken from the stored link. Never the task, the excerpt, worker messages, questions, options, answers or delegated task titles.
- Events: the newest 60 job events across all jobs (`JobStore.latestEvents`), each as type, from/to state, reason and code (each passed only if it is a short identifier), job id, project and host, and a one-line summary built from those codes. No request ids.
- Attention: a server-side list, most serious first, at most 40: credential rejected, not enrolled, unreachable (last check or engine backoff), credential expired or renewal failed; clients with no usable grant, families revoked for token reuse in the last 7 days, bearer tokens expiring within 14 days (with a `clients token` command that keeps the token's current `--access` and `--hosts`, every argument a single-quoted shell word, or, when no single pair says exactly that, a pointer to the client instead of a command, because the command's defaults are operate on every host), usable grants never observed; jobs waiting for an approval or a question, unconfirmed launches, failures in the last day, idle coordinators whose delegated work ended without a new turn; and the last check run's failures and warnings, except what the snapshot already shows live (a host's credential and renewal, and its T3 answer once a health result at least as new as the run is shown), so a failing public URL or exposure check is never "All clear". Each names where to act: a T3 thread link, a CLI command for the gateway machine, or a dashboard view.

**Run checks** (`DashboardChecks`, `src/dashboard/checks.ts`). Only on the operator's POST; no timer. Read-only. The network checks run in parallel with a five-second deadline each: a fresh `t3_environment_read` per host through the existing health path, the public URL's resource metadata (`probePublicUrl`, shared with `doctor`) and the dashboard exposure probe above. A host's deadline is absolute (`HOST_CHECK_DEADLINE_MS`): its health read may join a connection another caller is still initializing with the client's longer timeout, so past five seconds the check reports `t3_timeout` and the read is left to finish without touching that connection (its result is recorded with its own time, as any health read). In-process and synchronous, with no deadline: `PRAGMA quick_check` and the schema version, the data directory's permissions, the credential's state and last renewal, and the mint executable's resolution (`checkMintExecutable`; never executed, not even an explicit `mintPairingCodeProbe`, which `doctor` runs). Results are codes plus fixed text. One run at a time; a request within five seconds of the last run gets that run again (`reused`). Logged as `dashboard.checks_run` with counts only.

**The page** (`src/dashboard/assets/`). Plain HTML, CSS and one JavaScript module, served from memory with ETags; no framework, build step or external asset. The DOM is built with `createElement`, `createTextNode` and `setAttribute` only (no `innerHTML` or other HTML parsing, `eval`, inline styles or event-handler attributes), and only hash routes and validated `t3-thread://v1/<threadId>` or `t3-thread://v2/<environmentId>/<threadId>` links become `href`s, so any text the server sends, including names an unauthenticated registrant chose, is shown as text. The page loads the snapshot when opened, on **Refresh**, and when the tab becomes visible after a minute away; it contacts T3 only through **Run checks**. Views: Overview (headline, vital signs, a clients → gateway → hosts map, attention, recent activity), Clients, Hosts, Jobs (waiting or recent, open, finished, and the activity log) Webhooks (connect, replace key/URL, send test, disconnect and safe source/test status), and Checks (results, and what the checks cannot tell: a connector's own route, which hop of a tunnel failed, whether a connector still holds its token). Light and dark, keyboard and screen-reader friendly, with a bottom tab bar on phones.

**Demo** (`scripts/dashboard-demo.ts`, `scripts/lib/demo-fleet.ts`). A real gateway with a temporary data directory in front of fake T3 hosts, seeded through the gateway's own paths (OAuth sign-in, MCP tools, operator tokens, adoption) on a clock that catches up to now, in five scenarios. It reads no config or data directory of the operator's and contacts nothing beyond loopback; the dashboard shows a "Synthetic demo" badge unless `--no-badge`. `--webhook-receiver` adds local `/accept`, `/reject` and `/timeout` receiver paths for real setup requests with a fictional header. Demo management is restricted to literal loopback destinations; only this injected mode enables HTTP and a one-second test deadline. No real receiver is contacted.

## Security and privacy

- No secrets in the repository, examples, tests, or logs. Tests use generated values.
- Logs are JSON lines with ids, states, tool names, durations, and opaque client ids. Never tokens, approval or pairing codes, authorization headers, task text, worker messages, questions/options/answers, catalog content (T3 project names, models, options, constraints), or command stdout/stderr/argv. Worker messages, questions and catalogs are deliberately returned to authorized agents in tool output; they never enter logs or event details.
- Task text and message excerpts live only in the local database.
- Listen on loopback; expose through the operator's tunnel.
- Bound request body sizes and string lengths; validate all tool inputs with schemas.
- The approval page is the only HTML on the MCP listener; it is self-contained. The optional operator dashboard is served by a listener of its own (see "Operator dashboard").
- `SECURITY.md` explains how to report vulnerabilities and the threat model.

## Operations

- Developer compatibility checks are opt-in, via `scripts/check-t3-compatibility.ts`. They open the existing credential database read-only, discover MCP schemas in a separate session, compare the consumed tools (`orchestrator_capabilities` and the selected pending-request contract included) with an explicitly accepted private baseline, and smoke-test only reads through the gateway's existing parsers. No schedule, server hook, public tool/status field, migration or credential renewal is added. See operations.md, "Developer compatibility check", for coverage and baseline rules.
- `deploy/launchd/` template and installer for macOS (KeepAlive); a `systemd` user unit example for Linux.
- `t3-fleet-gateway doctor`: config validity, file permissions, database health, each host's reachability and credential expiry, mint command resolution and any explicit probe, public URL metadata, and with the dashboard enabled, that it answers on its loopback listener and that the public URL does not serve it. As built, the public URL check requires this gateway's own metadata (`resource` `<publicUrl>/mcp` and `resource_name` `t3-fleet-gateway`), not any server's metadata for the same resource.
- Graceful shutdown: stop accepting, finish in-flight requests, persist watcher state. As built: the HTTP server drains (up to 10 seconds), then the job engine stops after its current tick (a launch in progress completes or times out), then renewal stops and the database closes. The startup command preflight (`host.pairing_preflight`) is cancelled and not waited for; its late completion cannot start renewal. The startup model check (`project.model_missing`) is not waited for: shutdown aborts it, and a T3 call it still has in flight ends when the T3 clients close. The check also skips a host's remaining projects after the host fails once. Every job change is written when it happens, so there is nothing else to persist; a job left `dispatching` by a crash is reconciled at the next start.

- Agent path: an SDK client that performs registration, approval with a minted code, token exchange, refresh, and tool calls, including a request without `MCP-Protocol-Version`.
- Live end-to-end against a real T3 server: a script outside the automated suite, run against a scratch project. As built: `scripts/e2e-live.ts` (see `docs/operations.md`). The fake T3 (`test/helpers/fakeT3.ts`) implements the thread and pending-request tools from T3's published input and output schemas, with strict inputs so a misspelled field fails a test, and injects tool errors, delays, lost responses and bare HTTP statuses.

## Decisions log

- Gateway terminates MCP itself instead of proxying T3's MCP: agents get a small job-level contract, and client quirks are absorbed by our server.
- Downstream access level defaults to T3 "auto" (Full access) because the gateway enforces its own scopes and per-project runtime modes.
- The gateway polls T3 because T3 has no completion webhooks. Optional outbound gateway webhooks notify subscribers after those observations; they do not change T3 polling latency.
- v2 MCP SDK split packages over 1.x: current stable line, far fewer dependencies, serves both protocol eras (see Runtime).
- Own OAuth server on `node:http` instead of SDK helpers: v2 freezes its authorization-server helpers in a legacy package, and the rules here (approval codes, family revocation, grace window) need custom logic anyway.
- `/mcp` sets the `Accept` header of every POST to `application/json, text/event-stream` before the SDK transport sees it: the gateway always answers JSON, and the transports would otherwise refuse clients that send only `application/json` or a wildcard with `406`.
- 2025-era requests get a per-request stateless transport with JSON responses instead of the SDK handler's SSE-only legacy fallback, matching the JSON responses T3 itself sends to the same clients.
- Refresh grace window semantics: a retry of a rotated refresh token within two minutes gets a sibling pair and leaves the earlier sibling valid, because MCP clients refresh without a lock (two requests that both get a 401 both refresh) and keep whichever pair they saved last; retiring the first pair would log such a client out. Theft detection is kept by superseding the other siblings once one is rotated: presenting a superseded token, a rotated token after the grace window, or a token whose child was already rotated revokes the family. (Changed in round C; round A retired the earlier pair.) Access tokens of a superseded sibling are deliberately left valid until they expire. A process holding that pair is logged out at its next refresh either way (it presents a superseded refresh token), so revoking would only bring the logout forward; leaving them valid trades that delay for an equally long window for a thief (round D, restated in round E; the residual risk and the `accessTtlSeconds` advice are in docs/security.md).
- Operator-minted bearer tokens (`clients token`) are access tokens of a client of their own, not a separate credential type: verification, scopes, `clients list` and `clients revoke` stay one code path, and no migration was needed. They are for agents with no OAuth sign-in only; their risk (a static secret held by another service) is in docs/security.md.
- Global OAuth throttles are recoverable by the operator (minting a code lifts the approval pause; unapproved registrations stop counting after 10 minutes; `throttle reset`), because unauthenticated parties can fill them. Unapproved clients are still pruned only after a day, not after 10 minutes: an agent may show its approval link to a person who opens it much later, and pruning its registration would strand it.
- The approval form answers with a return page, not a `303` to the client (after a live approval with Grok Bot in Chrome stayed on the approval page): browsers enforce `form-action` across the whole redirect chain of a form submission and block silently, and a client's callback may redirect anywhere. T3 Code's own approval page avoids the same trap by posting with script and navigating to the returned `redirectTo`; a meta refresh does it without script. Errors for a `GET` of `/oauth/authorize` still redirect, since no form is involved. A repeated submission of an approved form gets the same response back rather than "code not accepted", because the operator's natural reaction to a page that did not move is to press Approve again.
- The package is not published to npm: Node does not strip types under `node_modules`, so it runs from a checkout (or `npm link`).
- A run on a found thread is what proves the task was delivered: a thread found with no run fails the job (`launch_not_started`) rather than looking finished (round E).
- T3 `isError` on a launch is a definite rejection only for codes T3 returns before creating anything; after any other error the marker is looked up once, because T3 documents that an error can leave a thread behind. Unknown launches are reconciled by the title marker, never relaunched. (Changed in round D; earlier rounds treated every launch error as definite.) `invalid_request` was confirmed live as refused before creation: after T3 refused a launch for want of a model, the project's thread list held no thread for it. Any failed lookup after a launch error leaves the job `unknown` (round E).
- Transport failures carry a delivery verdict in the T3 client rather than in the job layer, so every state-changing call (launch, send, interrupt, respond) can tell "nothing happened" from "may have happened".
- The shared T3 session is replaced only on session-level failures, never on a timeout, and resets are tied to the connection generation that failed: one slow call (such as a `fleet_status` health probe) must not lose the response of a launch in flight on the same session.
- A read-only call precedes launches so a dead keep-alive connection is discovered by a retryable read.
- `idle` frees a concurrency slot: a finished turn should not block the queue while it waits for review.
- Standing jobs (round F) let an agent drive a thread the operator already works in, rather than only threads it launched. Only the operator adopts one, from the CLI on the gateway machine, after the gateway has checked that the thread belongs to the named project; agents cannot attach to arbitrary threads. They hold no concurrency slot in any state. `work_cancel` interrupts their current turn and leaves them open (idle), since closing a person's coordinator is the operator's decision; a failed run leaves them idle for the same reason. Ending one is a new terminal state, `released`, rather than `cancelled` with a reason: `cancelled` means work_cancel stopped the thread, and here the thread is deliberately left running, which agents should be able to tell from the state alone. Adoption starts reading at the thread's end so a long history is not fed to agents as new activity. `allowWorkStart` is per project and defaults to `true`, so existing configs behave as before; turning it off is how an operator makes a coordinator the only way into a project, and the refusal names the coordinator so an agent can recover in one step.
- Coordinators that delegate (round I, from a live look at a T3 coordinator): the gateway does not try to keep a delegating coordinator `running`. Its run really is over, T3 would accept a new message as a new turn, and the honest state is `idle`; what changes is the advice. `waitingOnDelegatedWork` comes from the parent's own timeline (`subagent` items), not from reading child threads: the link between parent and child is not part of T3's documented read output, and the parent's item is what the coordinator itself waits on. Once the item's status while the child runs was confirmed live (`running`, then `completed`), the guidance was made to depend on the flag rather than on the reply text, and the case where the flag drops without a new turn (a failed or cancelled child) became an event of its own, `delegated_work_ended`, so a coordinator never sits waiting with agents told to send nothing. The followed tasks are capped (200) so a job row stays bounded; the count beyond the cap errs on the side of waiting. The gateway does not refuse `work_continue` on a job waiting on delegated work: the operator's agent may have a good reason (a correction, a cancellation of the plan), and T3 accepts it. Only an unsettled worker message holds the read position, so a long-lived pending item never hides later replies.
- Full replies are read live with `work_messages`, not carried in feed events or stored in full (after an agent missed parts of replies cut at the 2,000-character excerpt): `job_events` stays content-free and append-only, every feed poll stays small, and an agent pays for a message's text only when it asks for it. The excerpt stays for a quick look, flagged when cut. Only worker messages are returned, as for the excerpt, so no task text, follow-up or person's message is handed to a read-scope agent.
- Two views, two positions (after round I): round I looked for `subagent` items in reads that named no view, and T3's default view (`messages`) never returns them, so delegated work could not be detected against a real T3, while the fake (which had no views) passed. The messages view stays the source of the excerpt, the state and the read position (that path is proven live, and it skips the activity a busy coordinator produces); delegated work comes from the activity view with its own position, so a burst of reasoning or tool items delays only the activity read, never replies. The fake now models both views, and every read names its view.
- Per-host grants (v0.1.5) are scope strings rather than a stored host list: positive host scopes (`host:<id>:<level>`) beside the unchanged fleet scopes, so existing grants keep their meaning with no migration, refresh narrowing stays a subset check on strings, and removing a scope can never turn a restricted grant into a fleet-wide one (a negative or "restricted" marker would). Host scopes are not advertised in metadata, so SDKs keep requesting the fleet scopes and the operator chooses machines on the page; a fleet scope requested on refresh of a restricted grant is read as "keep my hosts at that level" rather than refused, so such a client is not cut off and gains nothing. Jobs on hosts a caller cannot read are indistinguishable from unknown ids, so ids cannot be probed across hosts.
- Permission approvals stay in T3: T3's MCP tools cannot answer them, so `work_respond` handles questions and `work_status` flags `waitingForApproval`.
- Follow-ups and interrupts use T3's `clientRequestId`, so the gateway can resend after an uncertain outcome without duplicating work.
- T3 statuses are parsed as strings and unknown ones count as active, so a T3 upgrade cannot make the watcher declare work finished.
- Migrations are append-only from migration 2 on, because a deployment now has a database at version 1 with jobs in it (until then migration 1 was corrected in place). Migration 2 rebuilds `jobs` to add the `released` state to its CHECK constraint, copying every row, with foreign keys off for the rebuild and checked before the commit (SQLite's documented procedure); a fresh database runs the same migrations, so new and upgraded databases have one schema. Because migration 1 changed in place before it was frozen, a version 1 database made by an earlier build may differ from today's migration 1, so migration 2 takes the columns to copy from `PRAGMA table_info(jobs)` at run time: a missing `state_changed_at` is filled from `updated_at`, a missing `t3_thread_link` stays NULL, a text `read_position` becomes an integer (NULL when it is not one), and any other missing column that cannot be NULL stops the migration with an error naming it (round I; the procedure changed, the schema it produces did not). Any failure inside `migrate`, SQLite's included (`SQLITE_BUSY` when another process holds the database past the busy timeout), is a `database_error` naming the migration; its transaction is rolled back.
- The service runs from a checkout of its own, separate from any checkout used for development: there is no build step, so the code a restart runs is whatever is in `REPO_DIR` at that moment. The launchd installer waits until `launchctl bootout` has finished (launchd unloads asynchronously, and an immediate `bootstrap` fails with an I/O error) and retries a failed bootstrap once.
- `serve` handles uncaught exceptions and unhandled rejections itself. Node 26.0's bundled undici sets the socket's type of service while writing a request from the socket's `connect` handler; on macOS that fails with EINVAL when the peer has already reset the connection, and the throw escapes the request (which then fails separately with a connection reset). That one error is logged and ignored, and counts as not delivered should it ever reach the T3 client as a request failure, since nothing was written. Any other uncaught error is treated as fatal: log name and code only, shut down within 10 seconds, exit `1`, and let the supervisor restart the process. The handlers are installed by `serve` for its lifetime only, never on import, so other commands and code using the modules keep Node's default behavior.
- The operator dashboard (v0.1.8) is a second loopback listener rather than routes on the MCP listener: the MCP listener is what a public tunnel carries, so a route there would be one tunnel rule away from the internet, and a separate port cannot be reached through it unless the tunnel is pointed at that port, which `doctor` and the dashboard's own checks detect through the real public URL. It has no login of its own: the tailnet-only proxy is the boundary; v0.1.9 extends that trust to managing webhook destinations without returning stored secrets. The management session bounds retries and is not authentication; Host, Funnel-header, custom-header, fetch-metadata and Origin checks keep other origins and rebinding out. A page load never contacts T3, so opening the page on a phone cannot load the hosts or turn into a monitor; reachability shows the last host contact with its age, background environment probes bound idle-host staleness, and Run checks asks immediately. Job titles are shown (T3 shows the same text as the thread title) but no task text, reply, question or delegated task title, and errors only as codes with fixed text, because messages can carry paths, URLs or text T3 returned. The page is plain HTML, CSS and JavaScript with no build step, matching the rest of the project, and builds its DOM without HTML parsing so names chosen by unauthenticated registrants stay text.


### Job pull request snapshots

The watcher uses `thread.pullRequests` when present and the optional read-only `list_thread_pull_requests({threadId})` otherwise. The client takes T3's answer as it comes (an object with a `pullRequests` array) and `readPullRequests` judges each entry on its own: `host`, `repository`, a positive integer `number`, a `state` of open, closed, merged or null, and an HTTPS GitHub-style URL on that host whose path is `/owner/repo/pull/number` (no port, credentials, query or fragment). T3 lists `repository` in lower case while its URL keeps GitHub's casing, so host, owner and repository are compared without regard to case; the `pull` segment has to be the lowercase one GitHub serves (`/PULL/23` is a 404) and the number canonical (no leading zeros). The URL itself is stored and shown exactly as T3 gave it. An entry that fails is skipped, a repeat of a PR (same host, repository and number, any case) counts once, and extra downstream title/branch fields are discarded. There are two bounds. A job follows up to 200 PRs, the stored list (`MAX_TRACKED_PULL_REQUESTS`, in key order): beyond that it keeps every open PR first, then the rest, newest (highest number) first within each group. Everything shown or sent carries at most 20 of them, chosen the same way and listed in that order (`displayPullRequests`): the job views and their text, webhook payloads and the dashboard. So a long-running coordinator's older PRs may be left out of what is shown, and the job tools say so (`20 of 35 shown`, `20 of 200+ shown` at the bound). A list that has entries but none valid is unknown and retains the last successful cache; an empty list is a known empty snapshot. These optional calls have a three-second deadline, use the client's existing read-only transport retry, and never affect host backoff or job state on failure. Each host tick budgets four observations; oldest attempts go first, at most once per job per minute. There is no additional timer. Failed attempts are throttled in memory and retried after restart.

Migration 13 adds nullable `pull_requests` JSON and `pull_requests_checked_at`. NULL is unknown/unbaselined and [] is known empty. Existing/adopted jobs baseline silently. Newly launched/reconciled jobs begin with [] so their first linked open PR is reported. Freshness-only checks do not bump job `updatedAt` or prolong attention. Snapshot, freshness, PR events and webhook outbox commit atomically under the watcher's existing snapshot guard. Each observation emits at most one `pull_request_opened` and one `pull_request_merged` event, each representing all changes of that kind in its snapshot. An unlink or unknown state never implies a merge. A subsequent unlink/relink or reopen can emit a new event. Events compare the two followed lists in full: a PR whose state became open or merged raises the event of that kind, and so does a PR the previous list did not hold, in either state. Only a list at the 200-PR bound is a window onto a longer one: there a PR leaving it raises nothing, and a PR the previous list did not hold counts as new only if it outranks that list's last entry (an old PR coming back into the list because another one left is not news). Below the bound nothing was left out, so a PR that opens and merges between two polls, or a followed PR that merges among more than 20, is reported. The PR an event is about may not be among the 20 shown. Known limit: a stored list of exactly 200 is treated as a window even when T3 listed no more, so on such a job a PR that opens and merges between two polls while older PRs are unlinked can go unreported; telling a complete list of 200 from a cut one would take one more stored bit, which no job has needed.

`work_status`/`work_list` expose only cached authorized metadata, with the last successful check time; terminal jobs stop refreshing. T3's own PR sync can lag GitHub. No GitHub API credential is added, and unlinked PRs or child PRs not linked to the parent remain invisible. PR event details contain fixed reasons only. PR webhook types are opt-in and carry at most 20 references (number/state/URL), without titles or branches, so the payload stays inside its 16 KiB bound for ordinary links however many PRs the job follows (an oversized one is still counted as `payload_limit` overflow). Existing default subscription settings and route identities stay unchanged. Dashboard snapshots reduce at most 20 references per job to number/state and never add arbitrary external links or call T3.
